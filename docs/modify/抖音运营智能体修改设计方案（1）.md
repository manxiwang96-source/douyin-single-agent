> 本文档是当前已锁定的下一改造套餐，供后续实现直接执行。
> 标识符、环境变量、接口路径、表名、状态值保持英文。密钥只写本地 `.env`，不入库、不写本文档。
> [langgraph.com.cn](https://langgraph.com.cn) 只作框架对照，禁止把文档示例整段复制进仓库。
> 历史文档保持原样：`docs/小红书运营机器人MVP方案.md`、`docs/modify/个人超级助理改造方案.md`、`docs/summary/` 复盘文档不改写。
> 不要改同学 C 的 Dify 工作流。本轮只定方案、改文档和文档测试，不写工人业务代码。

## 1. 先用白话说清楚

这个仓库现在跑的是「个人超级助理」：能聊天、能按要求写笔记、能生图生视频、能记事情、能发晨报邮件。

下一版要改成 **抖音运营智能体**。它还是一个会被主管 agent 调度的 **单个工人**，不是主管，也不是同学 C 的 Dify。用户以后不是技术人员，不会自己装 Python 或 Postgres，只会打开一个客户端 App，连到一台已经部署好的本地服务器。

打开客户端之后也不是直接聊天。正式入口是：

```text
登录 → 得到 user_id
新建智能体 → 展示能力（生图、生视频、评论+私信…）→ 用这个智能体 → 开始对话
 → app_threads(user_id, thread_id)
ainvoke(..., configurable={thread_id, user_id, agent_instance_id})
```

v1 一个用户只建这一个 `douyin_ops`；能力只展示，不勾选。

它要继续会聊天、生图、生视频；另外要能叫同学 C 已经写好的 Dify 工作流 `douyin-lead-discovery`，去做抖音评论和私信。以后还可以再接更多工作流，所以调用方式要规范：传输固定、产品工具固定，不要每加一个工作流就改一张图。

v1 闭环不是「先出草稿等人审」，而是 **一次调用就把线索扫描和真实发送做完**：

```text
用户说要做某话题评论/私信
  → discover_douyin_leads
  → difyctl run douyin-lead-discovery（no_send=false）
  → 回写 job / snapshot / list_comment / list_message
  → 聊天告知扫了什么、发了什么、失败了什么
```

对用户必须说「会真实发送」，不要说「先出草稿」。

真正登录抖音、搜视频、发评论/私信、刷新页面确认的，还是同学 C 的链路。我们负责听懂用户、排任务、调用这一条 Dify、把结果记下来、按用户把数据隔开。C 的 HTTP 服务器现在还没开，Dify 也还没发布；所以现在先把方案写死，live 真发以后再做。

## 2. 我们在大项目里是哪一块

整个项目是多智能体协同。职责要划清，否则表会重复、状态会对不上。

| 角色 | 谁做 | 干什么 |
| --- | --- | --- |
| 主管 agent | 另一位同学，合同以后再对接 | 以后调度这个工人 |
| 本仓库 | 我们 | 抖音运营智能体：对话、生图生视频、记忆、定时任务表、调用 Dify、回写结果 |
| Dify 工作流 | 同学 C | `douyin-lead-discovery`：编排登录、搜视频、拉评论、打分、发评论/私信、刷新确认 |
| 客户端 App | 以后给用户下载 | 登录、新建智能体、展示能力、用这个智能体开对话、聊天、看结果、下载图片视频。用户不直接碰服务器和数据库 |

**为什么这样拆：** 本仓库现在就不会登录/发布任何平台。C 已经把浏览器自动化和状态机做在 Dify 后面。我们若再做一套登录发评，就是重复建设，也和 C 的状态对不齐。主管合同未知，现在不要为它改图、加 Supervisor、加 MCP 服务。

本仓库必须能单独跑。主管以后再来挂载。

## 3. 已经拍板的总原则

| 主题 | 选择 | 为什么 |
| --- | --- | --- |
| 产品名 | 抖音运营智能体 | 平台从「特指小红书」改到抖音；小红书文案能力改成抖音口吻，不另做一套图 |
| 图拓扑 | 继续 `START -> chatbot -> tools_condition -> tools -> chatbot` | 现有 HITL、记忆、测试都挂在这张图上；不要为了接 Dify 把图拆散 |
| 调 Dify | `difyctl` 适配器 + **一个**现有 ToolNode 工具 `discover_douyin_leads` | 见第 6 节。不再拆成两个产品工具 |
| 唯一契约 | 只调 Dify `douyin-lead-discovery` | 不要同时调 C 的 CLI。Dify 已经把扫描编排做好了 |
| 真发 | `no_send=false` = 真发 | 真发发生在 Dify 第一步 `POST /v1/commands/run`；「列表-评论 / 列表-私信」只是把结果捞回来 |
| 密钥 | 默认不用 App API Key，用 `difyctl` 登录一次 | 见第 7 节 |
| 部署 | 方案 B：一台本地服务器，多个普通用户账号 | 用户不是技术人员 |
| 数据主库 | 全在服务器 Postgres | 8 点任务、多设备都不能绑在某一台手机上 |
| 客户端 | 只缓存，不当事真相源 | 「给用户下载」是 App，不是把表拆到手机里 |
| 人工审核 | 表按 HITL 设计，但 v1 抖音触达不审 | 生图生视频继续 `interrupt()`；评论/私信 Dify 已经在发，我们这边不再审 |
| 定时任务 | 现在建表，实现可以后做 | 用户会说「每天八点评论私信某话题」；表现在不定，后面只能推倒 |
| 任务取消 | 必须能手动取消，也能对话取消 | 见第 13 节。进行中取消未必能停住 Dify/C 已经在发的任务 |
| 客户端入口 | 登录 → 新建智能体 → 展示能力 → 用这个智能体 → 对话 | 见第 8.1 节；正式 App 不是打开就聊 |
| v1 智能体数量 | 每用户一个 `douyin_ops` 实例 | 多个智能体后续再迭代；实例表现在就要建 |
| 能力清单 | 只展示，不勾选、不裁工具 | 勾选会逼出按能力改图；v1 不做 |
| 用户隔离 | 业务表带 `user_id`；对话/任务/触达/媒体/抖音账号投影再带 `agent_instance_id`；官方 LangGraph 表不改 | 见第 11 节 |
| 主管合同 | 先不管 | 未知板块，现在加了也是猜 |
| Dify 发布 | 后续再做 | 当前草稿、0 个已发布版本、无 API Key。现在只定方案 |
| 改 Dify | 不改 | 同学 C 的工作流已经写好，我们只调用 |

旧锁定里「两个工具、先扫 `--no-send`、人审后再发、两次 `difyctl`、`DIFY_COMMENT_APP_ID` / `DIFY_DM_APP_ID`、默认 `require_approval=true`、待审 API 为 v1 必需」**全部作废**。这些名字下文写成「不再采用」，避免实现时再抄回去。

## 4. 产品改成什么，保留哪些能力

保留：

- 多轮对话
- 生图、生视频，以及现有对话里的 `interrupt()` 审核卡
- 长期记忆（按用户隔离）
- 以后仍可能要的定时任务能力（表先建）

改掉：

- 产品人设从「个人超级助理 / 特指小红书」改成「抖音运营智能体」
- 点名写稿时，口吻和结构按抖音，不再套小红书笔记模板
- 新增抖音评论 + 私信：只通过一个工具调用 C 的 Dify

不做：

- 本仓库自己登录抖音、自己发评论私信
- 工人内部再做一个主管
- 把 C 的浏览器自动化再写一遍
- 把 C 的全量扫描库镜像过来
- 一边调 Dify、一边再调 CLI

## 5. 对话图为什么先不改

现有图：

```text
START -> chatbot -> tools_condition -> tools -> chatbot
                              \-> END
```

节点仍然只有 `chatbot` 和 `tools`。`parallel_tool_calls=False`。

**为什么不加节点：** 评论和私信对模型来说就是「要不要调用一个工具」，和现有的 `search_kb`、`send_email` 同类。不要加 `dify_comment` 这类专用节点。加了就要改路由、改 HITL、改测试，而 Dify 内部的扫描编排本来就不该出现在我们图上。

**为什么不用 `create_react_agent`：** 现网已经是教程图 + 自定义状态 + 工具内 `interrupt()`。换成预置 ReAct 会和「对照官网、不改现有写法」冲突。

**为什么现在不做 Supervisor：** 主管是别人的板块。工人内部自己调度自己，会和以后的主管叠床架屋。

FastAPI 继续 `ainvoke`。以后挂主管时，优先把这张已编译的图当工人能力用，不要先拆成另一套图。

## 6. 调用同学 C 的 Dify：为什么是工具，不是 MCP，也不是新节点

讨论过三种接法：做成 MCP 工具、做成图节点、做成现有 ToolNode 里的普通工具。选定第三种，分三层：

1. **传输层** `DifyClient.run(name, inputs) -> {ok, name, workflow_run_id, status, outputs, error}`
2. **一个 LangChain 工具**，并进现有 ToolNode：`discover_douyin_leads(...)`（实现时名称可微调，文档先锁这个）
3. **工作流登记表**，按 Dify App ID 找工作流，而不是一张图一个节点

默认传输是服务器上的 `difyctl`。HTTP + App API Key 只当备用。

**为什么不是本仓库再包一个 MCP：** 仓库里已有的 MCP 是星期几和广州天气，和 Dify 不是一类事。官方 `difyctl skills install` 是给编程助手发现工具用的，不是给这个 FastAPI 工人用的。我们自己再开一个 MCP 进程，多一跳失败点，主管以后也还要再调一次。规范调用 = 固定传输 + 固定一个产品工具 + 以后只加登记项。

**为什么不是图节点：** 评论和私信是「模型决定要不要调用」的动作。C 的扫描编排是 Dify 画布内部的事，不应在我们图里再画一遍。

不再采用两个产品工具 `reply_douyin_comment` / `send_douyin_dm`。C 的这条工作流已经把「扫描 + 真发 + 把评论列表和私信列表捞回来」收成一次 run。我们再拆两个工具，就会对同一条工作流调两次，或者假装还有一个独立发送 App——当前工作空间里并没有。

### 6.1 扫描编排是什么

扫描编排不是我们图上的新节点，也不是本仓库去开浏览器。它是同学 C 在 Dify 里排好的步骤，用来按顺序调用她的 HTTP：

1. `POST /v1/commands/run`（异步；`no_send=false` 时这里就会真发）
2. 轮询 `GET /v1/jobs/{id}`（最多 40 次、每次 sleep 3s）
3. `GET /v1/snapshot`
4. 列表-评论
5. 列表-私信

所以「列表-评论 / 列表-私信」不是发送节点，只是把已经发生的结果捞回来。发送工作流以后若 C 另做，再登记；v1 不依赖它。

只读核对过的本地 Dify（Community `1.17.0`，地址只写内网主机，不写账号密码）：

- App 名：`douyin-lead-discovery`
- 模式：workflow
- 当前是草稿：已发布版本 0、无 API Key、`tool_published=false`
- 因此现在不能 live 真跑；方案仍按这条契约写

### 6.2 为什么选 Dify，不选 CLI，也不双调

同学 C 那边其实还有 CLI / HTTP。v1 **只认 Dify 这一条契约**，不要 LangGraph 既 `difyctl run` 又 subprocess 调 CLI。

| 方式 | 优点 | 缺点 | v1 结论 |
| --- | --- | --- | --- |
| 调 Dify 工作流 | C 已经把扫描编排写好；我们不碰 cwd/venv；以后她改画布，我们尽量只改映射；`difyctl` 可以不配 App API Key | 多一跳：工人 → Dify → C 的 HTTP；草稿未发布时跑不了；取消未必能停内层 job | **采用** |
| 调 CLI | 少一跳；命令颗粒度更细（`run/list/send/message`） | 要绑她的工作目录和配置；我们会把她已经编排好的步骤再写一遍；和「Dify 已做好」重复 | **不采用** |
| 同时调两个 | 看起来更稳 | 双发、状态对不齐、取消更乱 | **禁止** |
| 直读她的 SQLite | 字段现成 | 双写会把状态写乱 | **禁止** |

### 6.3 工具对外暴露什么，服务器自己填什么

Dify 输入变量名已经从草稿开始节点读到，实现时按这些名字映射，不要再猜：

```text
base_url, api_token, account, video_id, keyword, limit, channels, no_send, auto_login, list_status
```

Dify 输出：

```text
job_id, run_response, job_status, job_response, snapshot, list_comment, list_message
```

工具给模型的，只留业务字段：

- `account`（必填）
- `keyword` 或 `video_id`
- `limit`
- `channels`
- `list_status`

服务器配置自己填，不让模型碰：

- `base_url`（C 的 HTTP，只写变量名，不写密码）
- `api_token`（只进服务器 `.env`）
- `no_send=false`（v1 锁真发，不要再写死 `no_send=true`）
- `auto_login`

`inputs` / `outputs` 仍整份进 `workflow_runs` 的 JSONB，方便以后变量有增减。

一次用户请求通常只调 **一次** `difyctl run`。不要假设还要再调一次发送工作流。短时间相同 `account + keyword + video_id` 要防重入，避免模型连点两次就双发。

## 7. 为什么可以不用 Dify 工作流密钥

可以。默认走 `difyctl` 的 OAuth 登录，不把每个工作流的 App API Key 写进 `.env`。

做法：

- 在 **服务器这台机器** 上由人执行一次 `difyctl auth login`（设备码，token 前缀 `dfoa_`，Windows 进凭据管理器）
- 配置里只放 App ID：`DIFY_LEAD_APP_ID`（可写 App ID 或 App 名 `douyin-lead-discovery`）。不再采用 `DIFY_COMMENT_APP_ID`、`DIFY_DM_APP_ID`
- 调用类似：`difyctl run app <app_id> --inputs '{...}'`
- 自建 Dify 要打开官方 CLI 需要的开关（`OPENAPI_ENABLED`、`ENABLE_OAUTH_BEARER`）
- `difyctl` 版本必须和同学 C 的 Dify 版本匹配。当前已核对是 Community **1.17.0**，实现时下载对应 `difyctl`

**为什么密钥不按用户存：** `difyctl` 登录的是服务器操作系统用户，不是 App 里的 `user_id`。v1 整台服务器共用一个 Dify 工作空间。按用户映射 Dify 身份是以后的事，token 更不能放到手机上。

工人不能自己弹出浏览器登录。退出码 4 / `auth_expired` 只能提示管理员重新登录。HTTP + API Key 只在 `difyctl` 不可用时备用，密钥仍只在服务器 `.env`。

## 8. 部署：给非技术人员用的本地服务器

锁定方案 **B**。

用户不会装 Python、Postgres、Dify。他们下载客户端，连局域网/内网里那台已经部署好的服务器。

服务器上有：FastAPI 工人、Postgres、APScheduler、difyctl、同学 C 的 Dify、图视频热存储。

客户端上有：聊天、任务取消、下载媒体、本地缓存。v1 没有「待审列表」产品入口，因为评论/私信不在我们这边审。

**为什么不能做成「每人电脑一份 Postgres」：** 数据会散掉，8 点任务在手关机时跑不了，换手机历史就没了。本地部署 ≠ 数据在手机里。

### 8.1 客户端入口

用户不是技术人员，最后用的是本地部署的服务器 + 下载下来的客户端。入口必须让后端分清「谁」「用哪个智能体」「哪一次对话」：

```text
登录 → app_users / user_id
新建智能体 → INSERT agent_instances(user_id, template_code=douyin_ops)
展示能力 → 只读模板清单，不勾选、不裁工具
用这个智能体 → INSERT app_threads(user_id, agent_instance_id, thread_id)
之后 ainvoke(..., configurable={thread_id, user_id, agent_instance_id})
```

**为什么要多「智能体实例」这一层：** 「新建智能体」和「开对话」不是同一步。如果只写 `app_threads(user_id, thread_id)`，后端没法记住用户点过「用这个智能体」，以后一个人多个智能体也无处挂载。v1 虽一人一实例，表要先按这个模型建。

**为什么能力只展示：** 用户看懂「这个工人会干什么」即可。勾选会变成按能力裁工具、甚至每实例 compile 新图，和「图不改」冲突，也超出 v1。

**图仍然不改：** `START -> chatbot -> tools_condition -> tools -> chatbot`。能力清单是给前端展示的配置，不是图上的新节点。

## 9. 人工审核为什么表还在，v1 却不审评论私信

这里要分清两件事：

1. **表还按 HITL 设计。** 以后如果产品又要人审，只改开关，不改表。
2. **v1 抖音触达不走审批。** 同学 C 已确认：不用审核；`no_send=false` 时列表-评论和列表-私信对应的是已经真实发布的结果。Dify 在审的话我们这边就不审。

| 通道 | 用在哪 | 机制 | 为什么 |
| --- | --- | --- | --- |
| 对话媒体 | 生图、生视频 | 继续工具内 `interrupt()`，类型 `review_media` | 一次生成挡住当前对话即可，现有审核卡能用 |
| 评论/私信 | C 的 Dify 真发 | 表字段保留 `proposed` / `ready_to_send` / `approved_reply` / `require_approval`，但 v1 `require_approval=false`，**不做待审 API** | Dify 第一步已经发了；我们再审就会「人还没点同意，评论已经出去了」 |

8 点任务以后实现时，也是同一个工具、同样 `no_send=false`。人审开关仍留在 `job_definitions.require_approval`，默认 false。若以后要审批，再把扫描和发送拆开；现在不要假装还能拦下来。

## 10. 同学 C 的链路怎么接到我们的表上

C 的 **链路 B：线索发现 → 评论 / 私信触达**。她原来的产品图仍值得对照，方便排障；但 v1 我们不在自己这边复刻「先扫后审再发」的门禁。

### 10.1 四段（发生在 Dify / C HTTP 内部）

- **B1 登录选视频：** `login / check`，关键词搜索，视频 `discovered → selected`
- **B2 扫描与评估：** 拉评论入库，LLM 打分过滤，生成候选回复
- **B3 评论发送：** `no_send=false` 时在 `POST /v1/commands/run` 里真发，发后核对原文是否出现
- **B4 私信发送：** 同样在这次 run 里真发，发后刷新私信页核对

我们只调用一次 Dify，把输出回写到 `engage_*`。不再打一遍分，不再改她的回复再发给她。

### 10.2 人工门禁（v1 我们不执行）

C 的旧文档里有：run 默认 `--no-send`，账号暂停或状态不是 `ready_to_send` 禁止发送。那是她内部状态机，不是我们 v1 的产品门禁。

v1 明确：

- 不要再把 `--no-send` 当默认
- 不要等 `ready_to_send` 才允许调用 Dify
- 发送失败重试、截图、原文核对由 C / Dify 保证；我们只记最终结果

### 10.3 状态机（表上仍保留，用来落库和排障）

视频：

```text
discovered → selected → scanning → replying | failed | needs_login → completed
```

评论：

```text
proposed → ready_to_send → sending → sent | failed | needs_login | cancelled
```

私信：

```text
proposed → ready_to_send → sending → sent | failed | needs_login | cancelled
```

v1 从 Dify 输出回写时，多数行会直接落到 `sent` / `failed` / `needs_login`。`proposed`、`ready_to_send`、`approved_reply` 列仍在，给以后审批用，不当 v1 必经门。

### 10.4 所有权（避免两套真相）

| 谁 | 存什么 | 角色 |
| --- | --- | --- |
| 同学 C / Dify 自己的库 | 登录会话、全量扫描评论、浏览器动作、重试细节、截图原件 | 运营真相源。「拉评论入库」发生在这里 |
| 本仓库 Postgres | 用户、对话、任务、**被选中的视频**、Dify 返回的评论/私信结果 | 产品真相源 |
| 用户手机/电脑 | 登录态、草稿、已下载图视频、最近会话缓存 | 缓存 |
| LangGraph 官方表 | `checkpoints*`、`store` | `setup()` 生成，禁止 ALTER，禁止拆到手机 |

**为什么不镜像 C 的全量评论：** 扫描量会很大，这才是库膨胀的来源之一。用户要看的是「这次发了什么 / 失败了什么」，不是每一条被丢掉的低分评论。两边用 `platform_video_id` / `platform_comment_id` 对齐。不要直接读 C 的 SQLite。

## 11. 数据库怎么设计

原则：

1. 不改官方 LangGraph 表。官方短记忆靠 `thread_id`，长记忆靠 Store 的 namespace，不靠我们给官方表加 `user_id` 或 `agent_instance_id`。
2. `app_users` 只带用户身份。`agent_instances` 带 `user_id`。对话、任务、触达、媒体、抖音账号投影同时带 `user_id` 和 `agent_instance_id`。工具从 `RunnableConfig` 读这两个业务 id，不要让模型传「我是谁」「用哪个智能体」。
3. 状态用 `TEXT + CHECK`，词汇跟 C 走，方便对排障。
4. 半结构化、输出样例还可能变的字段用 JSONB。
5. 时间用 `TIMESTAMPTZ`。外键列自己建索引。

对照官方用法：生产 `PostgresSaver` + `PostgresStore`，测试仍 `InMemorySaver`。跨用户记忆的 namespace 从现在的 `("assistant", "profile")` 改成 `(user_id, "profile")`。v1 一人一实例，长记忆先按用户分，不按实例再拆一层。任务幂等不再只写 `("assistant", "jobs")`，改走下面的任务表。

v1 不单独建可编辑的 `agent_templates` 表。模板 `douyin_ops` 写在服务器配置里，能力文案给前端只读展示，例如：多轮对话、生图、生视频、抖音评论+私信。以后多人多模板再考虑模板表。

### 11.1 `app_users`

本地多用户。先留 `login_name`、`password_hash`，登录产品以后再做。没有这张表，后面所有 `user_id` 都无处安放。登录这一步只产生 `user_id`，还不等于已经有一个智能体。

### 11.2 `agent_instances`

一次「新建智能体」一行。字段要点：`user_id`、`template_code`（v1 固定 `douyin_ops`）、`title`、`status`。

`status`：

```text
draft | active | archived
```

v1 每个 `user_id` 最多一个 `status=active` 的实例（部分唯一索引）。若用户点第二次「新建」，应复用已有 active 实例，而不是再插一行。

### 11.3 `app_threads`

一次「用这个智能体」开对话一行。带 `user_id`、`agent_instance_id`、`thread_id`。`status`：`active | interrupted | closed | archived`。

**为什么要：** 现在线程集合在内存里（`app.state.threads`），进程一重启就丢，也无法按用户、按智能体过滤。官方 checkpoint 表不能加列，所以用这张旁路表做「这个会话属于谁的哪个智能体」。点「用这个智能体」时才 INSERT 这一行。

### 11.4 `douyin_accounts`

每个用户在某个智能体实例下的抖音账号 **投影**。带 `user_id`、`agent_instance_id`。`status`：`active | paused | needs_login`。不存 cookie。

**为什么要：** C 规定账号暂停或 `needs_login` 时她内部会失败。客户端要能显示「请重新登录抖音」。cookie 属于 C 的运行时，我们只记结果。

### 11.5 `job_definitions` / `job_runs`

定义：`user_id`、`agent_instance_id`、`kind`（`douyin_topic_engage`，以及以后的 `morning_brief` / `hydrate`）、`cron`、时区默认 `Asia/Shanghai`、`enabled`、`require_approval` 默认 false、`payload JSONB`（话题、是否评论、是否私信）。

运行：一次 8 点执行一行。同样带 `user_id`、`agent_instance_id`。`status`：

```text
scheduled | running | waiting_review | sending | succeeded | failed | skipped | cancelled
```

`UNIQUE (job_id, scheduled_for)`，避免同一点钟跑两遍。

`waiting_review` 仍留着，给以后审批用。v1 抖音 8 点实现时，一次 `discover_douyin_leads`（`no_send=false`）跑完就 `succeeded` / `failed`，不进待审。

**为什么现在就建：** 实现可以后做，但「每天八点评论私信某话题」已经确定要有。没有定义表和运行表，后面只能继续滥用全局 Store 键，多用户会串。任务挂在智能体实例上，取消时也按这个范围找。

### 11.6 `workflow_runs`

一次 `difyctl run` 一行。带 `user_id`、`agent_instance_id`。`inputs JSONB`、`outputs JSONB`、`workflow_run_id`、`dify_app_id`、`status`、`error`。

**为什么单独建：** 这是和 C 对账的审计表，不要和业务状态机混在一张宽表里。v1 一次任务通常一行；以后若再接发送工作流，也还是一行一次调用。

### 11.7 `engage_videos`

只存这次任务 **选中的** 视频，不存搜索全量。状态跟 C 的视频状态机：

```text
discovered → selected → scanning → replying | failed | needs_login → completed
```

字段要点：`user_id`、`agent_instance_id`、`job_run_id`、`thread_id`、`platform_video_id`、`keyword`、`status`、标题/链接、时间戳。

### 11.8 `engage_comments`

状态跟 C 的评论状态机：

```text
proposed → ready_to_send → sending → sent | failed | needs_login | cancelled
```

关键字段：`user_id`、`agent_instance_id`、`platform_comment_id`、`video_id`、原文、分数、`candidate_reply`、`approved_reply`、`require_approval`、`attempt_count`（上限 2）、核对结果、`screenshot_uri`。

v1 `require_approval=false`。结果从 Dify 的 `list_comment` / `snapshot` 回写，不经待审 API。`approved_reply` 列保留，不当门禁。

### 11.9 `engage_dms`

状态跟 C 的私信状态机；列仍保留 `proposed`：

```text
proposed → ready_to_send → sending → sent | failed | needs_login | cancelled
```

同样带 `user_id`、`agent_instance_id`。可按 `video_id` 筛选。v1 从 `list_message` 回写最终 `sent/failed`。

### 11.10 `media_assets`

本仓库生图生视频的元数据，不是 C 的截图。带 `user_id`、`agent_instance_id`。`storage_status`：`stored | offloaded | expired | missing`。文件默认服务器保留 7 天；客户端下载后可提前 offload。截图只存 URI，不进数据库二进制。

路径按 `outputs/{user_id}/images|videos` 分用户，避免互看。v1 一人一实例，目录先按用户分即可。

### 11.11 明确不建

- Dify 工作流定义表（C / Dify 自己有）
- 可编辑的 `agent_templates` 表（v1 配置写死 `douyin_ops`）
- 抖音 cookie、LLM Key、SMTP 授权码表（只在 `.env` / 系统凭据）
- 把 checkpoint 消息再抄一份聊天业务表
- 把 C 扫到的低分评论整库镜像过来
- 给官方 `checkpoints*` / `store` 加 `user_id` 或 `agent_instance_id` 列

### 11.12 运行时怎么串起来

```text
登录 → app_users / user_id
新建智能体 → INSERT agent_instances(user_id, template_code=douyin_ops)
展示能力 → 只读模板清单，不勾选、不裁工具
用这个智能体 → INSERT app_threads(user_id, agent_instance_id, thread_id)
之后 ainvoke(..., configurable={thread_id, user_id, agent_instance_id})
remember_fact -> store.put((user_id, "profile"), ...)
对话里要评论/私信 -> discover_douyin_leads -> workflow_runs + 回写 engage_*
08:00（后做）-> job_runs + 同一个工具（no_send=false）
用户取消 -> 见第 13 节
生图生视频 -> 仍 interrupt，只用于媒体
```

今天代码里的缺口，实现时要改掉：

- 没有 `agent_instances`，也没有「新建智能体 / 用这个智能体」这两步落库
- `PROFILE_NAMESPACE = ("assistant", "profile")` 是全局的，必须改成 `(user_id, "profile")`
- `JOBS_NAMESPACE = ("assistant", "jobs")` 是全局的，改走任务表
- `main.py` 的 `ainvoke` 现在只传 `thread_id`，要实现时传入 `user_id` 和 `agent_instance_id`
- 现有 `POST /v1/threads` 无用户、无实例，正式 App 不够用
- `app.state.threads` 是内存 set
- 媒体目录还没按用户分开

## 12. 哪些在服务器，哪些在用户设备

服务器 Postgres：上面所有业务表 + LangGraph 官方表。这是唯一真相源。

服务器磁盘：图视频热文件、C 返回的截图 URI 对应文件。会过期。

服务器操作系统凭据：`difyctl` OAuth。不是 SQL 行。

Dify 自己的库：工作流定义和内部日志。我们只留 `workflow_run_id`。

客户端可以有本地 SQLite，但只是缓存：

- `local_session`：登录本系统的 token
- `local_agent_cache`：当前智能体标题和能力文案（只读缓存）
- `local_thread_cache`：最近会话标题/摘要
- `local_drafts`：还没提交的改稿
- `local_media_files`：已下载的图视频（这才是体积大的东西）
- `sync_cursor`：上次拉结果的时间

**不能放客户端当主库：** `agent_instances`、`job_*`、`engage_*`、`workflow_runs`、`douyin_accounts`、checkpoints。智能体实例标题可以缓存，但 `agent_instances` 不能当客户端主库。

**为什么「数据太多」不能靠拆表到手机解决：** 真正大的是生成文件和 C 的全量扫描。文件让用户下载后服务器可删；扫描全量根本不应进我们的库。把任务表放到手机，手关机 8 点任务就停了。

## 13. 定时任务：先建表，后实现，必须能取消

例：「每天八点定时抖音评论和私信某相关的话题」。

调度仍用 FastAPI lifespan 里的 APScheduler。OSS 没有 LangGraph Platform Cron，不要假造。时区 `Asia/Shanghai`。任务在服务器跑，不依赖手机在线。

实现可以后做，但表和取消规则现在锁死。以后 8 点也是同一个工具、`no_send=false`。

### 13.1 一次 8 点怎么走

```text
08:00 APScheduler
  -> 若定义已被取消/关闭：不创建 run，或 run=skipped
  -> job_runs = running
  -> 若抖音账号 paused / needs_login：禁止调用，run=failed 或 skipped
  -> discover_douyin_leads / difyctl run（no_send=false）
  -> 写入 workflow_runs + engage_videos / engage_comments / engage_dms
  -> 聊天或任务页告知扫了什么、发了什么、失败了什么
  -> succeeded | failed
```

对话里「帮我评这个话题」用同一套表，只是 `job_run_id` 为空、`thread_id` 有值。

### 13.2 取消：手动也可以，对话也可以

用户必须能停掉任务，不能「设了 8 点就只能改数据库」。两条入口，写同一张表。

**取消以后都别跑（取消定义）**

- 客户端关掉开关
- 或用户说「以后每天八点这条停掉」「取消那个定时评论」

结果：`job_definitions.enabled=false`。以后到期不再创建 `job_runs`。已经 `sent` 的评论/私信不撤回。

**取消这一次（取消当前 run）**

- 任务页点取消
- 或用户说「今天这条别发了」「取消这次抖音评论」

结果：当前 `job_runs.status=cancelled`。还没发出去的本地行改为 `cancelled`。已经 `sent` 的不撤回。

**正在跑时取消**

- 我们标 `cancelled`
- **未必能停 Dify/C 已在发的任务**（她的轮询和 HTTP job 我们控不住）
- 结果回来后：不再当成功任务展示；能识别未发送的不再二次调用；已 `sent` 不撤回
- 已成功/已失败：不能再取消，只能关掉以后的定义

**对话取消怎么接图**

现有 ToolNode 里加 `list_jobs`、`cancel_job`（名称实现时再定，保持英文）。从 `RunnableConfig` 读 `user_id`，只能取消自己的任务。不要为取消再加图节点，也不要靠模型「口头答应取消」却不写表。

**手动取消**

客户端走 HTTP，例如 `POST /v1/jobs/{job_id}/disable`、`POST /v1/job-runs/{run_id}/cancel`（路径实现阶段可微调）。和对话工具改同一行数据。

取消是一等状态，不要用删行表示。删了就无法解释「8 点为什么没发」。
