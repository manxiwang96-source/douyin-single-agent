## 3. 当前问题和已确认原因

### 3.1 消息缺少可靠时间和稳定身份

`app/serialize.py` 当前消息返回内容主要是：

```json
{
  "role": "user|assistant",
  "content": "...",
  "media": []
}
```

缺少：

- `message_id`
- `client_message_id`
- `created_at`

前端 `ChatMessage` 也没有稳定的服务端消息身份和创建时间。

### 3.2 模型上下文没有可靠的服务端时间

`app/graph.py` 的 `_chat_payload` 当前主要是系统提示词加历史消息。历史消息没有显式时间标记。

`app/prompts.py` 目前主要要求模型必要时调用 `get_current_datetime`，不是每轮强制注入服务端当前时间。

因此模型容易混淆：

- 今天和昨天；
- 刚刚和之前；
- 同一 `video_id`/账号是否在今天发送过；
- 私信和评论是否是同一种发送行为。

### 3.3 前端按文本去重

`frontend/src/lib/chat.ts` 的 `withPendingUser` 当前按用户消息文本判断是否已经存在，类似：

```ts
item.role === "user" && item.content === text
```

这会导致相同文本连续发送时，第二条消息被错误合并或丢失。

### 3.4 前端超时早于后端 Dify 阻塞时间

当前前端普通 HTTP 超时时间约为 180 秒，而后端 Dify 配置或测试中可能允许等待约 300 秒。

前端先超时后，若直接清理 loading/pending 状态，就会造成“正在回复...”气泡消失，而后端可能仍在处理。

### 3.5 初始化和发送存在响应覆盖竞态

`ChatView.vue` 中 `bootstrap()` 异步加载线程，`send()` 同时可能先插入乐观用户消息。旧的 `getThread` 响应或旧发送响应可能直接替换整个消息列表，从而覆盖刚插入的用户气泡。

## 4. 总体设计结论

本次可以在现有架构上完成修复，不需要数据库表结构变更。

总体策略：

1. 后端为消息补充 `message_id`、`client_message_id`、`created_at`。
2. 将消息 metadata 随 LangGraph checkpoint 持久化。
3. 每轮调用模型时注入服务端当前时间、时区和历史消息时间。
4. 发送工具按实际业务发送时间和发送类型判断重复，而不是只按 `video_id`/账号判断。
5. 前端使用 `client_message_id` 和服务端 `message_id` 做乐观消息确认和合并。
6. 前端保留 pending、timeout、error 状态，不因为请求超时而删除消息。
7. 使用请求序号或版本保护，防止旧响应覆盖新消息。

## 5. 数据库边界：本次不改表结构

本次不要执行以下操作：

- 不新增 `thread_messages` 表；
- 不修改 LangGraph 官方 checkpoint 表；
- 不新增数据库 migration；
- 不 ALTER 现有业务表；
- 不把聊天消息复制成第二套事实源。

原因：

1. LangGraph checkpoint 已经负责保存对话状态。
2. 消息的 `message_id`、`client_message_id`、`created_at` 可以放入 LangGraph 消息的 metadata 或 `additional_kwargs`，随 checkpoint 持久化。
3. 现有业务表已经具备抖音发送历史和时间字段，至少包括：
   - `workflow_runs`
   - `engage_videos`
   - `engage_comments`
   - `engage_dms`
4. 新增独立聊天消息表会形成 LangGraph checkpoint 与业务消息表两个事实源，增加同步、去重和迁移复杂度。

只有在确认以下需求已经超出当前架构能力时，后续才重新评估新增聊天消息表：

- checkpoint 清理后仍要长期保留完整聊天审计；
- 按消息全文搜索或导出；
- 独立消息状态机；
- 消息级重试队列和审计报表。

如果执行时发现不修改数据库确实无法实现本套餐，先报告具体阻塞原因和影响，不要直接执行 migration。

## 6. 后端消息接口和 metadata

### 6.1 输入接口

修改 `app/main.py` 或实际定义 `MessageIn` 的位置：

为用户消息增加可选字段：

```python
client_message_id: str | None
```

要求：

- 兼容旧客户端不传该字段；
- 如果客户端传入，服务端原样关联到对应用户消息；
- 服务端仍然生成自己的 `message_id`，不能把客户端 ID 当作唯一服务端 ID。

### 6.2 消息生成

每条新消息由服务端生成：

- `message_id`
- `created_at`

时间来源必须是服务端，不能把浏览器时间作为最终权威时间。

使用项目已有的 `assistant_timezone` 配置，当前默认时区为：

```text
Asia/Shanghai
```

如果仓库中已经有时间工具或配置读取逻辑，优先复用，不要重复实现另一套时区配置。

### 6.3 消息序列化

修改 `app/serialize.py`，序列化消息时返回：

- `role`
- `content`
- `media`
- `message_id`
- `client_message_id`
- `created_at`

要求：

- 不破坏现有媒体、附件和消息内容格式；
- 旧 checkpoint 消息没有 metadata 时正常返回；
- 旧消息缺少时间时返回 `null` 或等价空值；
- 不允许把旧消息的时间伪造成当前时间；
- 时间格式要稳定，建议使用 ISO 8601 或项目现有统一格式。

### 6.4 线程响应

线程 API 顶层建议增加：

```json
{
  "timezone": "Asia/Shanghai",
  "messages": []
}
```

如果当前接口已有顶层结构，保持兼容，只补充时区或消息字段，不要无故重命名现有接口字段。

## 8. 抖音发送记录和日期判断

检查：

- `app/leads.py`
- 相关发送记录查询；
- 相关工具定义；
- 现有测试和业务表字段。

判断是否已经发送过时，至少结合：

- `video_id`；
- 账号；
- 发送类型：私信或评论；
- 发送时间；
- 发送状态。

必须正确处理以下场景：

### 场景 A：昨天发送过，今天没有发送

- 昨天相同 `video_id` 和账号发送过；
- 今天尚未发送；
- 今天再次请求发送。

结果：不能因为昨天存在记录就判断“今天刚刚发送过”。

### 场景 B：今天发送过

- 今天同一账号、同一 `video_id`、同一发送类型已有成功记录。

结果：根据现有业务规则阻止今天重复发送，并向模型返回明确原因。

### 场景 C：不同账号

结果：不同账号之间不能互相影响。

### 场景 D：不同发送类型

结果：私信和评论不能无条件互相去重。

### 场景 E：失败或未完成记录

结果：失败、取消、超时、未完成状态不能被误认为成功发送。

如果当前工具按存在性查询，需要改成明确的当天时间范围查询：

```text
当日开始时间 <= sent_at < 次日开始时间
```

时间边界必须使用项目配置的 `assistant_timezone`，不能混用浏览器时区或服务器 UTC 的自然日判断。

## 10. 前端乐观消息和消息合并

### 10.1 发送顺序

发送消息时必须按以下顺序：

1. 生成 `client_message_id`，建议使用 `crypto.randomUUID()`；
2. 立即插入用户乐观消息；
3. 用户消息渲染后，再插入智能体 pending 气泡；
4. 发起后端请求；
5. 后端返回后确认和替换对应消息。

### 10.2 消息匹配优先级

正式服务端消息和本地乐观消息合并时，使用以下优先级：

1. `messageId`；
2. `clientMessageId`；
3. 明确的本地 pending 标识。

禁止只按 `content` 判断消息是否已存在。

相同文本连续发送两次必须显示两条独立用户消息。

### 10.3 防止旧响应覆盖新消息

为 `bootstrap()`、`getThread()`、`send()` 和 resume 等异步操作增加请求序号、版本号或等价保护：

- 旧的初始化响应不能覆盖刚插入的用户消息；
- 旧发送响应不能覆盖更新的消息列表；
- 只有当前有效请求的结果才允许更新对应状态；
- 服务端线程列表缺少尚未确认的本地 pending 消息时，保留本地消息；
- 不要简单用一次整体替换丢弃本地消息。

## 11. Dify 超时、失败和 pending 状态

修改：

- `frontend/src/api/http.ts`
- `frontend/src/api/threads.ts`
- `frontend/src/views/ChatView.vue`

要求：

1. 普通 API 可以保留普通超时时间。
2. 聊天发送和 resume 使用独立长超时。
3. 长超时时间必须覆盖后端 Dify 最大等待时间，并预留响应收尾时间。
4. 前端请求超时后不能直接删除 pending 气泡。
5. 用户消息必须始终保留。
6. 智能体 pending 气泡必须保留，或转为明确的超时处理中状态。
7. 请求超时后结束 loading，但页面显示可见提示。
8. 请求成功后，正式智能体消息替换对应 pending 气泡。
9. 请求真正失败后，保留用户气泡并显示错误状态。
10. 不允许静默删除用户消息或智能体状态消息。

建议显示文案：

```text
正在回复...
等待超时，后台可能仍在处理
本次回复失败，请重试
```

这次不要求增加 SSE，不要求修改 Dify 工作流，不要求实现后台轮询新接口。

如果现有后端请求超时后仍可能继续执行，前端提示必须避免误导用户认为后台一定已经停止。

## 18. 验收标准

只有同时满足以下条件才算完成：

- 新用户消息和智能体消息能够显示服务端具体时间；
- 旧消息没有时间时不会被伪造为当前时间；
- 模型能够根据服务端日期和实际发送记录区分今天、昨天和更早记录；
- 昨天的相同 `video_id`/账号记录不会被当成今天刚发送；
- 私信、评论、账号和发送状态判断不会互相错误污染；
- 相同文本连续发送不会被错误去重；
- 用户消息先显示，智能体 pending 气泡后显示；
- 初始化或旧请求响应不能覆盖新消息；
- Dify 超时后用户消息和智能体状态气泡不会消失；
- 真正失败时仍有明确错误状态；
- 数据库表结构没有变化；
- 相关测试和完整测试全部通过；
- 已创建中文 Git commit。
