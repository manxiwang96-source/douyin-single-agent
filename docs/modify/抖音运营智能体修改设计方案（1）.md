# 抖音运营智能体修改设计方案（1）

> 本文档是当前已锁定的下一改造套餐，供后续实现直接执行。
> 标识符、环境变量、接口路径、表名、状态值保持英文。密钥只写本地 `.env`，不入库、不写本文档。
> [langgraph.com.cn](https://langgraph.com.cn) 只作框架对照，禁止把文档示例整段复制进仓库。
> 历史文档保持原样：`docs/小红书运营机器人MVP方案.md`、`docs/modify/个人超级助理改造方案.md`、`docs/summary/` 复盘文档不改写。

## 1. 先用白话说清楚

这个仓库现在跑的是「个人超级助理」：能聊天、能按要求写笔记、能生图生视频、能记事情、能发晨报邮件。

下一版要改成 **抖音运营智能体**。它还是一个会被主管 agent 调度的 **单个工人**，不是主管，也不是同学 C 的 Dify。用户以后不是技术人员，不会自己装 Python 或 Postgres，只会打开一个客户端 App，连到一台已经部署好的本地服务器。

打开客户端之后也不是直接聊天。正式入口是：登录得到 `user_id` → 点「新建智能体」→ 看到能力清单（生图、生视频、抖音评论+私信等）→ 点「用这个智能体」才开对话。v1 一个用户只建这一个 `douyin_ops`；能力只展示，不勾选。

它要继续会聊天、生图、生视频；另外要能叫同学 C 做好的 Dify 工作流，去做抖音评论和私信。以后还可以再接更多工作流，所以调用方式要规范，不要每加一个工作流就改一张图。

同学 C 的链路不是「模型直接发一条评论」这么简单，而是：

1. 登录、按关键词选视频
2. 把评论拉下来、打分、生成候选回复（默认不发）
3. 人改完回复再发评论，发后核对原文
4. 再发私信，发后刷新页面核对文本和时间

所以我们的表必须能对上这套状态机，但我们自己不去登录抖音、不去刷页面。真正干活的是 C 的 Dify；我们负责听懂用户、排任务、等人审、记录结果、按用户把数据隔开。

## 2. 我们在大项目里是哪一块

整个项目是多智能体协同。职责要划清，否则表会重复、状态会对不上。

| 角色 | 谁做 | 干什么 |
| --- | --- | --- |
| 主管 agent | 另一位同学，合同以后再对接 | 以后调度这个工人 |
| 本仓库 | 我们 | 抖音运营智能体：对话、生图生视频、记忆、定时任务、人工审核、调用 Dify |
| Dify 工作流 | 同学 C | 登录抖音、搜视频、拉评论、打分、发评论/私信、刷新页面确认 |
| 客户端 App | 以后给用户下载 | 登录、新建智能体、展示能力、用这个智能体开对话、聊天、待审列表、下载图片视频。用户不直接碰服务器和数据库 |

**为什么这样拆：** 本仓库现在就不会登录/发布任何平台。C 已经把浏览器自动化和状态机做在 Dify 里。我们若再做一套登录发评，就是重复建设，也和 C 的状态对不齐。主管合同未知，现在不要为它改图、加 Supervisor、加 MCP 服务。

本仓库必须能单独跑。主管以后再来挂载。

## 3. 已经拍板的总原则

| 主题 | 选择 | 为什么 |
| --- | --- | --- |
| 产品名 | 抖音运营智能体 | 平台从「特指小红书」改到抖音；小红书文案能力改成抖音口吻，不另做一套图 |
| 图拓扑 | 继续 `START -> chatbot -> tools_condition -> tools -> chatbot` | 现有 HITL、记忆、测试都挂在这张图上；不要为了接 Dify 把图拆散 |
| 调 Dify | `difyctl` 适配器 + 两个现有 ToolNode 里的工具 | 见第 6 节 |
| 密钥 | 默认不用 App API Key，用 `difyctl` 登录一次 | 见第 7 节 |
| 部署 | 方案 B：一台本地服务器，多个普通用户账号 | 用户不是技术人员 |
| 数据主库 | 全在服务器 Postgres | 8 点任务、人工审核、多设备都不能绑在某一台手机上 |
| 客户端 | 只缓存，不当事真相源 | 「给用户下载」是 App，不是把表拆到手机里 |
| 人工审核 | 现在就按 HITL 设计表，默认要人审 | 以后关掉审批只改开关，不改表 |
| 定时任务 | 现在建表，实现可以后做 | 用户会说「每天八点评论私信某话题」；表现在不定，后面只能推倒 |

| 客户端入口 | 登录 → 新建智能体 → 展示能力 → 用这个智能体 → 对话 | 见第 8.1 节；正式 App 不是打开就聊 |
| v1 智能体数量 | 每用户一个 `douyin_ops` 实例 | 多个智能体后续再迭代；实例表现在就要建 |

| 用户隔离 | 业务表带 `user_id`；对话/任务/触达/媒体/抖音账号投影再带 `agent_instance_id`；官方 LangGraph 表不改 | 见第 11 节 |
| 主管合同 | 先不管 | 未知板块，避免空设计 |
| 框架 | 对照 langgraph.com.cn，不粘贴示例代码 | 仓库已有自己的 `chatbot` + `tools` 写法 |

## 4. 产品改成什么，哪些先留着

对外身份从「个人超级助理」改成「抖音运营智能体」。

客户端正式入口是三步，不是打开 App 就进聊天：

1. 新建智能体
2. 展示能力（生图片、生视频、抖音评论+私信等），只呈现、不勾选
3. 用这个智能体，开始对话

v1 一个用户暂时只建这一个；多个智能体、能力勾选都后续再迭代。

继续提供：

- 多轮对话
- 明确要求时写抖音文案（知识库、标题/正文/标签改成抖音规范）
- 生图、生视频，生成前仍要人审
- 跨对话记住用户事实
- 以后仍可保留晨报/喝水这类任务类型，但不再是产品主线

新增：

- 调用 C 的评论工作流、私信工作流
- 待审队列：用户改回复、批准、跳过
- 定时「按话题做评论+私信」，可取消
- 多用户：每个用户只能看见自己的对话、任务、待审、媒体

明确先不做：

- 本仓库登录抖音、存 cookie、自己发评
- 本仓库包一层新的 MCP 服务器给 Dify
- 本仓库加 `dify_comment` 图节点，或改成 `create_react_agent`
- 本仓库做 Supervisor
- 把 Postgres 表拆到用户手机
- 对外合同、主管挂载
- 现在就实现 8 点抖音任务（表先建好）
- 一人多个智能体实例
- 能力勾选、按勾选裁工具、每实例 compile 一张新图

## 5. 对话图为什么几乎不动

当前图：

```text
START -> chatbot -> tools_condition -> tools -> chatbot
                              \-> END
```

节点仍然只有 `chatbot` 和 `tools`。`parallel_tool_calls=False`。生图生视频仍在工具里面 `interrupt()`。

**为什么不加节点：** 多一个 Dify 节点，每拓展一个工作流就要改图、改边、改测试。工具注册表可以按 App ID 往上加，图不用动。

**为什么不用 `create_react_agent`：** 现有自定义 state（`last_image_path` / `last_video_path`）、工具内 HITL、测试都绑在手写图上。换工厂函数等于重写工人，和「对照官网、不改现有写法」冲突。

**为什么现在不做 Supervisor：** 主管是别人的板块。工人内部自己调度自己，会和以后的主管叠床架屋。

FastAPI 继续 `ainvoke`。以后挂主管时，优先把这张已编译的图当工人能力用，不要先拆成另一套图。

## 6. 调用同学 C 的 Dify：为什么是工具，不是 MCP，也不是新节点

讨论过三种接法：做成 MCP 工具、做成图节点、做成现有 ToolNode 里的普通工具。选定第三种，分三层：

1. **传输层** `DifyClient.run(name, inputs) -> {ok, name, workflow_run_id, status, outputs, error}`
2. **两个 LangChain 工具**，并进现有 ToolNode：`reply_douyin_comment(...)`、`send_douyin_dm(...)`
3. **工作流登记表**，按 Dify App ID 找工作流，而不是一张图一个节点

默认传输是服务器上的 `difyctl`。HTTP + App API Key 只当备用。

**为什么不是本仓库再包一个 MCP：** 仓库里已有的 MCP 是星期几和广州天气，和 Dify 不是一类事。官方 `difyctl skills install` 是给编程助手发现工具用的，不是给这个 FastAPI 工人用的。我们自己再开一个 MCP 进程，多一跳失败点，主管以后也还要再调一次。规范调用 = 固定传输 + 固定两个产品工具 + 以后只加登记项。

**为什么不是图节点：** 评论和私信是「模型决定要不要调用」的动作，和 `search_kb`、`send_email` 同类。C 的 B1–B4 是 Dify 内部的事，不应在我们图里再画一遍。

**输入变量名还没定：** 先把 `inputs` 存成 JSONB。工具对外先暴露稳定字段（`topic`、`video_id`、`require_approval` 等），真正发给 Dify 前由适配器映射。C 把变量名定下来再补映射，不改表。

一次任务通常至少调两次 Dify：先扫描（默认不发），人审后再发送（只带 `ready_to_send`）。不要假设一个工作流从搜视频一直跑到私信发出去。

## 7. 为什么可以不用 Dify 工作流密钥

可以。默认走 `difyctl` 的 OAuth 登录，不把每个工作流的 App API Key 写进 `.env`。

做法：

- 在 **服务器这台机器** 上由人执行一次 `difyctl auth login`（设备码，token 前缀 `dfoa_`，Windows 进凭据管理器）
- 配置里只放 App ID：`DIFY_COMMENT_APP_ID`、`DIFY_DM_APP_ID`，不放密钥
- 调用类似：`difyctl run app <app_id> --inputs '{...}'`
- 自建 Dify 要打开官方 CLI 需要的开关（`OPENAPI_ENABLED`、`ENABLE_OAUTH_BEARER`）
- `difyctl` 版本必须和同学 C 的 Dify 版本匹配（CLI 要求 ≥ 1.15.0 这一档，以 C 告知的版本为准）

**为什么密钥不按用户存：** `difyctl` 登录的是服务器操作系统用户，不是 App 里的 `user_id`。v1 整台服务器共用一个 Dify 工作空间。按用户映射 Dify 身份是以后的事，token 更不能放到手机上。

工人不能自己弹出浏览器登录。退出码 4 / `auth_expired` 只能提示管理员重新登录。HTTP + API Key 只在 `difyctl` 不可用时备用，密钥仍只在服务器 `.env`。

## 8. 部署：给非技术人员用的本地服务器

锁定方案 **B**。

用户不会装 Python、Postgres、Dify。他们下载客户端，连局域网/内网里那台已经部署好的服务器。

服务器上有：FastAPI 工人、Postgres、APScheduler、difyctl、同学 C 的 Dify、图视频热存储。

客户端上有：聊天、待审、下载媒体、本地缓存。

**为什么不能做成「每人电脑一份 Postgres」：** 数据会散掉，8 点任务在手关机时跑不了，换手机待审列表就没了。本地部署 ≠ 数据在手机里。

### 8.1 客户端入口

用户不是技术人员，最后用的是本地部署的服务器 + 下载下来的客户端。入口必须让后端分清「谁」「用哪个智能体」「哪一次对话」：

```text
登录 → app_users / user_id
新建智能体 → INSERT agent_instances(user_id, template_code=douyin_ops)
展示能力 → 只读模板清单，不勾选、不裁工具
用这个智能体 → INSERT app_threads(user_id, agent_instance_id, thread_id)
之后 ainvoke(..., configurable={thread_id, user_id, agent_instance_id})
```

**为什么要多「智能体实例」这一层：** 「新建智能体」和「开对话」不是同一步。如果只写 `app_threads(user_id, thread_id)`，后端没法记住用户点过「用这个智能体」，以后一个人多个智能体也无处挂载。v1 虽一人一实例，表要先按这个模型建。

**为什么能力只展示：** 用户看懂「这个工人会干什么」即可。勾选会变成按能力裁工具、甚至每实例 compile 新图，和「图不改」冲突，也超出 v1。

**图仍然不改：** `START -> chatbot -> tools_condition -> tools -> chatbot`。能力清单是给前端展示的配置，不是图上的新节点。

## 9. 人工审核为什么要两套

C 的图写得很清楚：默认可扫描、可评估，**默认不发**；账号暂停或状态不是 `ready_to_send` 禁止发送。

这和「生成一张图之前问一句」不是同一种审核。

| 通道 | 用在哪 | 机制 | 为什么 |
| --- | --- | --- | --- |
| 对话媒体 | 生图、生视频 | 继续工具内 `interrupt()`，类型 `review_media` | 一次生成挡住当前对话即可，现有审核卡能用 |
| 评论/私信 | C 的 B3/B4，含每天 8 点 | 表状态 + 客户端待审列表 | 一次可能几十条，不能把整条聊天卡住；手关机时任务也必须先跑完扫描 |

默认 `require_approval=true`。以后若用户说「不用问我直接发」，只改开关：扫描后直接标 `ready_to_send`。表不用改。

8 点任务即使要人审，也必须在服务器先跑完扫描。人审的是「拟好的回复」，不是「到点了手机在不在」。

## 10. 同学 C 的链路怎么接到我们的表上

C 的 **链路 B：线索发现 → 评论 / 私信触达**。

### 10.1 四段

- **B1 登录选视频：** `login / check`，关键词搜索，视频 `discovered → selected`
- **B2 扫描与评估：** 拉评论入库，LLM 打分过滤，生成候选回复
- **B3 评论审核发送：** 只取 `ready_to_send`，人工改 `approved_reply`，发后核对原文是否出现
- **B4 私信确认：** 可按 `video-id` 筛选，发后刷新私信页，文本完全一致，时间是刚刚/几秒前，或与当前相差 ≤ 2 分钟

### 10.2 人工门禁

- run 默认 `--no-send`
- 账号暂停，或状态不是 `ready_to_send`，禁止发送
- 发送失败最多重试 2 次，并保留截图

### 10.3 状态机（用来排障，不要跳状态）

视频：

```text
discovered → selected → scanning → replying | failed | needs_login → completed
```

评论：

```text
proposed → ready_to_send → sending → sent | failed | needs_login
```

私信：

```text
ready_to_send → sending → sent | failed | needs_login
```

产品若开审批，私信在交给 C 之前本地多一个 `proposed`。C 的图从 `ready_to_send` 起跳；人审发生在我们这边。

### 10.4 所有权（避免两套真相）

| 谁 | 存什么 | 角色 |
| --- | --- | --- |
| 同学 C / Dify 自己的库 | 登录会话、全量扫描评论、浏览器动作、重试细节、截图原件 | 运营真相源。「拉评论入库」发生在这里 |
| 本仓库 Postgres | 用户、对话、任务、审核队列、**被选中的视频**、**proposed 及之后** 的评论/私信 | 产品真相源 |
| 用户手机/电脑 | 登录态、草稿、已下载图视频、最近会话缓存 | 缓存 |
| LangGraph 官方表 | `checkpoints*`、`store` | `setup()` 生成，禁止 ALTER，禁止拆到手机 |

**为什么不镜像 C 的全量评论：** 扫描量会很大，这才是库膨胀的来源之一。用户要看的是「待我审的回复」和「发出去了没」，不是每一条被丢掉的低分评论。两边用 `platform_video_id` / `platform_comment_id` 对齐。C 的入参未定前，不直接读 C 的表。

## 11. 数据库怎么设计

原则：

1. 不改官方 LangGraph 表。官方短记忆靠 `thread_id`，长记忆靠 Store 的 namespace，不靠我们给官方表加 `user_id` 或 `agent_instance_id`。
2. `app_users` 只带用户身份。`agent_instances` 带 `user_id`。对话、任务、触达、媒体、抖音账号投影同时带 `user_id` 和 `agent_instance_id`。工具从 `RunnableConfig` 读这两个业务 id，不要让模型传「我是谁」「用哪个智能体」。
3. 状态用 `TEXT + CHECK`，词汇跟 C 走，方便对排障。
4. 半结构化、C 还没定的入参用 JSONB。
5. 时间用 `TIMESTAMPTZ`。外键列自己建索引。

对照官方用法：生产 `PostgresSaver` + `PostgresStore`，测试仍 `InMemorySaver`。跨用户记忆的 namespace 从现在的 `("assistant", "profile")` 改成 `(user_id, "profile")`。v1 一人一实例，长记忆先按用户分，不按实例再拆一层。任务幂等不再只写 `("assistant", "jobs")`，改走下面的任务表。

v1 不单独建可编辑的 `agent_templates` 表。模板 `douyin_ops` 写在服务器配置里，能力文案给前端只读展示，例如：多轮对话、生图、生视频、抖音评论+私信。以后多人多模板再考虑模板表。

### 11.1 `app_users`

本地多用户。先留 `login_name`、`password_hash`，登录产品以后再做。没有这张表，后面所有 `user_id` 都无处安放。登录这一步只产生 `user_id`，还不等于已经有一个智能体。

### 11.2 `agent_instances`

一次「新建智能体」一行。字段要点：`user_id`、`template_code`（v1 固定 `douyin_ops`）、`title`、`status`。

`status`：

```text
draft | active | archived
```

v1 每个 `user_id` 最多一个 `status=active` 的实例（部分唯一索引）。若用户再次点「新建智能体」，复用已有 active 行，不插第二条。

**为什么要：** 前端「新建智能体」必须落库。如果只在客户端记一下，换设备就丢了，服务器也不知道对话挂在哪个工人上。v1 虽然一人一实例，后面要做多个智能体时也不用推倒表。

**不能当客户端主库：** 这张表在服务器 Postgres。客户端最多缓存标题和能力文案。

### 11.3 `app_threads`

`thread_id` 等于 LangGraph 的 `thread_id`。必须带 `user_id` 和 `agent_instance_id`。`status`：`active | interrupted | closed | archived`。

**为什么要：** 现在线程集合在内存里（`app.state.threads`），进程一重启就丢，也无法按用户、按智能体过滤。官方 checkpoint 表不能加列，所以用这张旁路表做「这个会话属于谁的哪个智能体」。点「用这个智能体」时才 INSERT 这一行。

### 11.4 `douyin_accounts`

每个用户在某个智能体实例下的抖音账号 **投影**。带 `user_id`、`agent_instance_id`。`status`：`active | paused | needs_login`。不存 cookie。

**为什么要：** C 规定账号暂停或 `needs_login` 时禁止发送。客户端要能显示「请重新登录抖音」。cookie 属于 C 的运行时，我们只记结果。

### 11.5 `job_definitions` / `job_runs`

定义：`user_id`、`agent_instance_id`、`kind`（`douyin_topic_engage`，以及以后的 `morning_brief` / `hydrate`）、`cron`、时区默认 `Asia/Shanghai`、`enabled`、`require_approval` 默认 true、`payload JSONB`（话题、是否评论、是否私信）。

运行：一次 8 点执行一行。同样带 `user_id`、`agent_instance_id`。`status`：

```text
scheduled | running | waiting_review | sending | succeeded | failed | skipped | cancelled
```

`UNIQUE (job_id, scheduled_for)`，避免同一点钟跑两遍。

**为什么现在就建：** 实现可以后做，但「每天八点评论私信某话题」已经确定要有。没有定义表和运行表，后面只能继续滥用全局 Store 键，多用户会串。任务挂在智能体实例上，取消时也按这个范围找。

### 11.6 `workflow_runs`

一次 `difyctl run` 一行。带 `user_id`、`agent_instance_id`。`inputs JSONB`、`outputs JSONB`、`workflow_run_id`、`dify_app_id`、`status`、`error`。

**为什么单独建：** 一次 `job_run` 会对扫描和发送各调一次（以后还可能更多）。这是和 C 对账的地方，不要和业务状态机混在一张宽表里。

### 11.7 `engage_videos`

只存这次任务 **选中的** 视频，不存搜索全量。状态跟 C 的视频状态机：

```text
discovered → selected → scanning → replying | failed | needs_login → completed
```

字段要点：`user_id`、`agent_instance_id`、`job_run_id`、`thread_id`、`platform_video_id`、`keyword`、`status`、标题/链接、时间戳。

### 11.8 `engage_comments`

状态跟 C 的评论状态机：

```text
proposed → ready_to_send → sending → sent | failed | needs_login | cancelled
```

关键字段：`user_id`、`agent_instance_id`、`platform_comment_id`、`video_id`、原文、分数、`candidate_reply`、`approved_reply`、`require_approval`、`attempt_count`（上限 2）、核对结果、`screenshot_uri`。

`proposed` = 客户端待审。人改的是 `approved_reply`。发送工具只吃 `ready_to_send`。

### 11.9 `engage_dms`

状态跟 C 的私信状态机；产品审批时本地多 `proposed`：

```text
proposed → ready_to_send → sending → sent | failed | needs_login | cancelled
```

同样带 `user_id`、`agent_instance_id`。可按 `video_id` 筛选。发后按 C 的规则核对：文本完全一致，时间是刚刚/几秒前，或与当前相差 ≤ 2 分钟。

### 11.10 `media_assets`

本仓库生图生视频的元数据，不是 C 的截图。带 `user_id`、`agent_instance_id`。`storage_status`：`stored | offloaded | expired | missing`。文件默认服务器保留 7 天；客户端下载后可提前 offload。截图只存 URI，不进数据库二进制。

路径按 `outputs/{user_id}/images|videos` 分用户，避免互看。v1 一人一实例，目录先按用户分即可。

### 11.11 明确不建

- 可编辑的 `agent_templates` 表（v1 配置写死 `douyin_ops`）

- 把 checkpoint 消息再抄一份聊天业务表

### 11.12 运行时怎么串起来

```text
登录 → app_users / user_id
新建智能体 → INSERT agent_instances(user_id, template_code=douyin_ops)
展示能力 → 只读模板清单，不勾选、不裁工具
```

今天代码里的缺口，实现时要改掉：

## 12. 哪些在服务器，哪些在用户设备

服务器 Postgres：上面所有业务表 + LangGraph 官方表。这是唯一真相源。

服务器磁盘：图视频热文件、C 返回的截图 URI 对应文件。会过期。

服务器操作系统凭据：`difyctl` OAuth。不是 SQL 行。

Dify 自己的库：工作流定义和内部日志。我们只留 `workflow_run_id`。

客户端可以有本地 SQLite，但只是缓存：

- `local_session`：登录本系统的 token
- `local_agent_cache`：当前智能体标题和能力文案（只读缓存）
- `local_thread_cache`：最近会话标题/摘要
- `local_drafts`：还没提交的改稿
- `local_media_files`：已下载的图视频（这才是体积大的东西）
- `sync_cursor`：上次拉待审/已发的时间

**不能放客户端当主库：** `agent_instances`、`job_*`、`engage_*`、`workflow_runs`、`douyin_accounts`、checkpoints。智能体实例标题可以缓存，但 `agent_instances` 不能当客户端主库。

**为什么「数据太多」不能靠拆表到手机解决：** 真正大的是生成文件和 C 的全量扫描。文件让用户下载后服务器可删；扫描全量根本不应进我们的库。把任务表放到手机，手关机 8 点任务就停了，审核也会丢。

## 13. 定时任务：先建表，后实现，必须能取消

例：「每天八点定时抖音评论和私信某相关的话题」。

调度仍用 FastAPI lifespan 里的 APScheduler。OSS 没有 LangGraph Platform Cron，不要假造。时区 `Asia/Shanghai`。任务在服务器跑，不依赖手机在线。

实现可以后做，但表和取消规则现在锁死。

### 13.1 一次 8 点怎么走

```text
08:00 APScheduler
  -> 若定义已被取消/关闭：不创建 run，或 run=skipped
  -> job_runs = running
  -> 若抖音账号 paused / needs_login：禁止发送，run=failed 或 skipped
  -> difyctl 扫描（等价 --no-send）
  -> 写入 engage_videos / engage_comments / engage_dms
  -> 若 require_approval=true：
        评论/私信停在 proposed
        job_runs = waiting_review
        客户端出现待审列表（可改 approved_reply）
  -> 用户批准 -> ready_to_send
  -> difyctl 发送（只带 ready_to_send）
  -> sending -> sent | failed | needs_login
  -> 用 C 的确认规则回写 verified
  -> 失败 attempt_count+1，<2 可再发，截图 URI 留下
```

对话里「帮我评这个话题」用同一套表，只是 `job_run_id` 为空、`thread_id` 有值。

### 13.2 取消：手动也可以，对话也可以

用户必须能停掉任务，不能「设了 8 点就只能改数据库」。两条入口，写同一张表。

**取消以后都别跑（取消定义）**

- 客户端关掉开关
- 或用户说「以后每天八点这条停掉」「取消那个定时评论」

结果：`job_definitions.enabled=false`。以后到期不再创建 `job_runs`。已经 `sent` 的评论/私信不撤回。

**取消这一次（取消当前 run）**

- 待审列表点取消
- 或用户说「今天这条别发了」「取消这次抖音评论」

结果：当前 `job_runs.status=cancelled`。还在 `proposed` / `ready_to_send` 的评论和私信改为 `cancelled`。已经 `sent` 的不撤回。

**正在跑时取消**

- 扫描中：我们未必能立刻杀掉 Dify 进程；run 标 `cancelled`，扫描结果回来后不再写入待审、不进入发送
- 发送中：停止尚未发送的；已发送的保留
- 已成功/已失败：不能再取消，只能关掉以后的定义

**对话取消怎么接图**

现有 ToolNode 里加 `list_jobs`、`cancel_job`（名称实现时再定，保持英文）。从 `RunnableConfig` 读 `user_id`，只能取消自己的任务。不要为取消再加图节点，也不要靠模型「口头答应取消」却不写表。

**手动取消**

客户端走 HTTP，例如 `POST /v1/jobs/{job_id}/disable`、`POST /v1/job-runs/{run_id}/cancel`（路径实现阶段可微调）。和对话工具改同一行数据。

取消是一等状态，不要用删行表示。删了就无法解释「8 点为什么没发」。

#### 8. 取消、重试、去重

用户会说「取消每天八点那个任务」或点客户端取消。我们表已设计 `cancelled`。要问她：

- 扫描中能否 stop。
- 取消后：已 `sent` 不撤回；未发送的不再 `send`。她能否按 id 列表跳过。
- 失败重试上限 2、发后核对原文/时间 ≤2 分钟，是否由她保证，我们只记最终 `sent/failed`。
- 同一 `video_id` / `comment_id` 她已去重的，我们还要不要再去重。

#### 9. 分类规则我们还做不做

她已有：`intent=potential_customer`、清晰度 ≥60、`confidence` ≥0.85、`is_lead=true`，并生成 `proposed_reply` / `proposed_message`。

请确认：我们 **不再打一遍分**，只展示她给的草稿和原因。阈值是否可配；不通过的评论要不要回传 `exclude_reason`（我们默认不入库全量淘汰评论）。
