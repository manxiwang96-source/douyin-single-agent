> 历史文档保持原样：`docs/小红书运营机器人MVP方案.md`、`docs/modify/个人超级助理改造方案.md`、`docs/summary/` 复盘文档不改写。

## 1. 先用白话说清楚

这个仓库现在跑的是「个人超级助理」：能聊天、能按要求写笔记、能生图生视频、能记事情、能发晨报邮件。

下一版要改成 **抖音运营智能体**。它还是一个会被主管 agent 调度的 **单个工人**，不是主管，也不是同学 C 的 Dify。用户以后不是技术人员，不会自己装 Python 或 Postgres，只会打开一个客户端 App，连到一台已经部署好的本地服务器。产品形态要对齐腾讯元器那种「智能体广场 + 对话侧边栏」，而不是打开 App 就直接聊天。

打开客户端之后的正式入口是：

```text
登录 → 得到 user_id
点击「新建智能体」→ 弹出模板窗（v1 只有「抖音运营助手」= douyin_ops）
填写名称、简介、上传头像 → INSERT agent_instances
广场出现小卡片（头像、名称、简介、模式、创建时间/最近编辑时间）
点击卡片 = 用这个智能体 → 复用该实例最近一条 active 对话，没有则 INSERT app_threads
进入对话页（中间聊天 + 右侧只读侧边栏）
ainvoke(..., configurable={thread_id, user_id, agent_instance_id})
```

一个用户可以新建多个智能体（一人多实例）。v1 模板仍只有 `douyin_ops`，能力只展示，不勾选。名称在当前用户未归档实例里不能重复：大小写不算差异，名称里不能有空格或其他空白。点进对话不算最近编辑。

侧边栏给用户看：应用描述、应用开发要点、只读的单智能体模式、知识库板块、工作流名称、工具名称。模型栏先去掉。应用描述用目录里的 `capability_description`，不要直接把 `SYSTEM_PROMPT` 摊给用户。

它要继续会聊天、生图、生视频；另外要能叫同学 C 已经写好的 Dify 工作流 `douyin-lead-discovery`，去做抖音评论和私信。以后还可以再接更多工作流，所以调用方式要规范：传输固定、每个工作流一个产品工具、实例绑定表预留，不要每加一个工作流就改一张图，也不要把 Dify 再包成 MCP。

新建 `douyin_ops` 时，服务器自动绑定 `douyin-lead-discovery`，并给该实例写入一份抖音运营 demo 知识库。用户提问时，优先在这个实例的知识库里检索（在现有 `chatbot` 节点内必搜）；不够再走 ToolNode 里的 `search_kb` 补检索。知识库不能代替 Dify 去真扫真发。

v1 闭环不是「先出草稿等人审」，而是 **一次调用就把线索扫描和真实发送做完**：

```text
用户说要做某话题评论/私信
  → discover_douyin_leads
  → POST {DIFY_BASE_URL}/workflows/run（Bearer DIFY_API_KEY，no_send=false）
  → 回写 job / snapshot / list_comment / list_message
  → 聊天告知扫了什么、发了什么、失败了什么
```

对用户必须说「会真实发送」，不要说「先出草稿」。

真正登录抖音、搜视频、发评论/私信、刷新页面确认的，还是同学 C 的链路。我们负责听懂用户、排任务、调用这一条 Dify、把结果记下来、按用户和智能体实例把数据隔开。C 的 HTTP 服务器现在还没开，Dify 也还没发布；所以现在先把方案写死。等她发布并给出 Service API Key 后，再用 `POST /v1/workflows/run` 做 live 真发。

## 2. 我们在大项目里是哪一块

整个项目是多智能体协同。职责要划清，否则表会重复、状态会对不上。

| 角色 | 谁做 | 干什么 |
| --- | --- | --- |
| 主管 agent | 另一位同学，合同以后再对接 | 以后调度这个工人 |
| 本仓库 | 我们 | 抖音运营智能体：对话、生图生视频、记忆、定时任务表、调用 Dify、回写结果 |
| Dify 工作流 | 同学 C | `douyin-lead-discovery`：编排登录、搜视频、拉评论、打分、发评论/私信、刷新确认 |
| 客户端 App | 以后给用户下载 | 登录、广场新建智能体、点卡片用这个智能体、聊天、只读侧边栏、看结果、下载图片视频。用户不直接碰服务器和数据库 |

**为什么这样拆：** 本仓库现在就不会登录/发布任何平台。C 已经把浏览器自动化和状态机做在 Dify 后面。我们若再做一套登录发评，就是重复建设，也和 C 的状态对不齐。主管合同未知，现在不要为它改图、加 Supervisor、加 MCP 服务。

本仓库必须能单独跑。主管以后再来挂载。

## 3. 已经拍板的总原则

| 主题 | 选择 | 为什么 |
| --- | --- | --- |
| 产品名 | 抖音运营智能体 | 平台从「特指小红书」改到抖音；小红书文案能力改成抖音口吻，不另做一套图 |
| 产品形态 | 智能体广场 + 对话侧边栏 | 对齐腾讯元器：先选实例，再聊天；侧边说明这个应用能干什么 |
| 图拓扑 | 继续 `START -> chatbot -> tools_condition -> tools -> chatbot` | 现有 HITL、记忆、测试都挂在这张图上；不要为了接 Dify 或 RAG 把图拆散 |
| 调 Dify | HTTP + App API Key 适配器 + 现有 ToolNode 产品工具 | 见第 6 节。v1 一个工具 `discover_douyin_leads`；以后每个工作流一个具名工具。`difyctl` 不再采用 |
| 唯一契约 | v1 只调 Dify `douyin-lead-discovery` | 不要同时调 C 的 CLI。以后接更多工作流，也只从我们发布的目录里选 |
| 真发 | `no_send=false` = 真发 | 真发发生在 Dify 第一步 `POST /v1/commands/run`；「列表-评论 / 列表-私信」只是把结果捞回来 |
| 密钥 | v1 用已发布工作流的 Service API Key（`DIFY_API_KEY`）；`difyctl` OAuth 不再采用 | 见第 7 节。本机 OpenAPI 设备码 404，安装目录用户也打不开 |
| 部署 | 方案 B：一台本地服务器，多个普通用户账号 | 用户不是技术人员 |
| 数据主库 | 全在服务器 Postgres | 8 点任务、多设备都不能绑在某一台手机上 |
| 客户端 | 只缓存，不当事真相源 | 「给用户下载」是 App，不是把表拆到手机里 |
| 人工审核 | 表按 HITL 设计，但 v1 抖音触达不审 | 生图生视频继续 `interrupt()`；评论/私信 Dify 已经在发，我们这边不再审 |
| 定时任务 | 现在建表，实现可以后做 | 用户会说「每天八点评论私信某话题」；表现在不定，后面只能推倒 |
| 任务取消 | 必须能手动取消，也能对话取消 | 见第 13 节。进行中取消未必能停住 Dify/C 已经在发的任务 |
| 客户端入口 | 登录 → 新建智能体 → 填卡片资料 → 用这个智能体 → 对话 | 见第 8.1 节；正式 App 不是打开就聊。点卡片就是「用这个智能体」 |
| v1 智能体数量 | 一人多实例 | 广场要能摆多张卡片。模板仍只有 `douyin_ops` |
| 名称规则 | 同一用户未归档实例，`lower(title)` 唯一；禁止空白 | 大小写不算差异；空格无效，直接拒绝，不当成名字的一部分 |
| 能力清单 | 只展示，不勾选、不裁工具 | 勾选会逼出按能力改图或每实例 compile；v1 不做 |
| 应用描述 | `capability_description` ≠ `SYSTEM_PROMPT` | 前者给用户看功能；后者给模型。两边语义要对齐，但字段分开 |
| 模式 | 只读 `single`（单智能体模式） | `multi` 只预留取值。v1 不让用户切换，也不做 Supervisor |
| 知识库 | 实例级向量检索；新建时写入 demo | 在 `chatbot` 内必搜；`search_kb` 只做补检索。v1 不开放用户上传 |
| 用户隔离 | 业务表带 `user_id`；对话/任务/触达/媒体/抖音账号/绑定/知识库再带 `agent_instance_id`；官方 LangGraph 表不改 | 见第 11 节 |
| 最近编辑 | 改名称/简介/头像才更新 `updated_at` | 点进对话不算最近编辑。对话活跃可另记 `app_threads.last_active_at` |
| 主管合同 | 先不管 | 未知板块，现在加了也是猜。若以后主管要 MCP，包的是本工人 HTTP，不是 Dify |
| Dify 发布 | 后续再做 | 当前草稿、0 个已发布版本、无 API Key。现在只定方案 |
| 改 Dify | 不改 | 同学 C 的工作流已经写好，我们只调用 |

旧锁定里「两个工具、先扫 `--no-send`、人审后再发、两次 `difyctl`、`DIFY_COMMENT_APP_ID` / `DIFY_DM_APP_ID`、默认 `require_approval=true`、待审 API 为 v1 必需、一人一个 `douyin_ops`、第二次新建就复用」**全部作废**。这些名字下文写成「不再采用」，避免实现时再抄回去。

## 4. 产品改成什么，保留哪些能力

保留：

- 多轮对话
- 生图、生视频，以及现有对话里的 `interrupt()` 审核卡
- 长期记忆（按用户 + 智能体实例隔离）
- 以后仍可能要的定时任务能力（表先建）

改掉：

- 产品人设从「个人超级助理 / 特指小红书」改成「抖音运营智能体」
- 点名写稿时，口吻和结构按抖音，不再套小红书笔记模板
- 新增抖音评论 + 私信：只通过产品工具调用 C 的 Dify
- 入口改成广场卡片 + 对话侧边栏；一个用户可以有多张 `douyin_ops` 卡片
- 每个实例自带一份 demo 知识库，回答时优先检索该实例内容

不做：

- 本仓库自己登录抖音、自己发评论私信
- 工人内部再做一个主管
- 把 C 的浏览器自动化再写一遍
- 把 C 的全量扫描库镜像过来
- 一边调 Dify、一边再调 CLI
- 把 Dify 再包成 MCP
- 用户自己填 Dify App ID / API Key
- 广场标签、收藏、模型选择栏

## 5. 对话图为什么先不改

现有图：

```text
START -> chatbot -> tools_condition -> tools -> chatbot
                              \-> END
```

节点仍然只有 `chatbot` 和 `tools`。`parallel_tool_calls=False`。

**为什么不加节点：** 评论和私信对模型来说就是「要不要调用一个工具」，和现有的 `search_kb`、`send_email` 同类。不要加 `dify_comment` 这类专用节点。加了就要改路由、改 HITL、改测试，而 Dify 内部的扫描编排本来就不该出现在我们图上。

**为什么不用 `create_react_agent`：** 现网已经是教程图 + 自定义状态 + 工具内 `interrupt()`。换成预置 ReAct 会和「对照官网、不改现有写法」冲突。

**为什么现在不做 Supervisor：** 主管是别人的板块。工人内部自己调度自己，会和以后的主管叠床架屋。

FastAPI 继续 `ainvoke`。以后挂主管时，优先把这张已编译的图当工人能力用，不要先拆成另一套图。

## 6. 调用同学 C 的 Dify：为什么是工具，不是 MCP，也不是新节点

讨论过三种接法：做成 MCP 工具、做成图节点、做成现有 ToolNode 里的普通工具。选定第三种，分四层：

1. **传输层** `DifyClient.run(name, inputs) -> {ok, name, workflow_run_id, status, outputs, error}`
2. **具名 LangChain 工具**，并进现有 ToolNode。v1 只有 `discover_douyin_leads(...)`（实现时名称可微调，文档先锁这个）。以后每接一个已发布工作流，就加一个具名产品工具，不要做通用的 `run_dify_workflow`
3. **产品目录**（服务器配置，不是可编辑表）：登记 `workflow_code`、展示名、对应产品工具、给用户看的功能说明。用户只能选我们发布过的项，不能填任意 Dify App ID / Key
4. **实例绑定表** `agent_instance_workflows`：只记这个实例启用了哪个 `workflow_code`。密钥仍在服务器 `.env`，不进绑定表

v1 默认传输是已发布工作流的 HTTP Service API：`POST {DIFY_BASE_URL}/workflows/run`，请求头 `Authorization: Bearer {DIFY_API_KEY}`。`difyctl` 登录 / `difyctl run` **不再采用**（本机 OpenAPI 设备码 404，资源管理器也打不开安装目录）。

新建 `douyin_ops` 时自动插入一行绑定：`workflow_code=douyin-lead-discovery`、`enabled=true`。

**怎么按实例裁工具，却不每实例 compile 一张图：**

```text
HTTP / 定时任务入口
  → 读 agent_instance_workflows
  → configurable.allowed_workflow_codes = 已启用的 code 列表
  → chatbot 里 bind_tools(子集)
  → ToolNode 仍挂全部产品工具的并集
  → 每个 Dify 工具自己再检查当前实例是否绑定
```

图还是编译一次。`ainvoke` 继续带 `configurable={thread_id, user_id, agent_instance_id}`，另外在同一份 configurable 里放 `allowed_workflow_codes`。

**为什么不是本仓库再包一个 MCP：** 仓库里已有的 MCP 是星期几和广州天气，已经通过 `extra_tools` 进同一 ToolNode，和 Dify 不是一类事。官方 `difyctl skills install` 是给编程助手发现工具用的，不是给这个 FastAPI 工人用的。我们自己再开一个 MCP 进程去包 C 的 Dify，会多一跳失败点，还会把 `user_id` / `agent_instance_id` 和密钥稀释到天气 MCP 进程里。以后自定义智能体要接更多 Dify 工作流，仍然走 ToolNode + `DifyClient` + 目录/绑定，不把 Dify 封装成 MCP。若以后主管需要 MCP，包装的是 **本工人的 HTTP**，不是同学 C 的 Dify。

**为什么不是图节点：** 评论和私信是「模型决定要不要调用」的动作。C 的扫描编排是 Dify 画布内部的事，不应在我们图里再画一遍。

不再采用两个产品工具 `reply_douyin_comment` / `send_douyin_dm`。C 的这条工作流已经把「扫描 + 真发 + 把评论列表和私信列表捞回来」收成一次 run。我们再拆两个工具，就会对同一条工作流调两次，或者假装还有一个独立发送 App——当前工作空间里并没有。

### 6.1 扫描编排是什么

扫描编排不是我们图上的新节点，也不是本仓库去开浏览器。它是同学 C 在 Dify 里排好的步骤，用来按顺序调用她的 HTTP：

1. `POST /v1/commands/run`（异步；`no_send=false` 时这里就会真发）
2. 轮询 `GET /v1/jobs/{id}`（最多 40 次、每次 sleep 3s）
3. `GET /v1/snapshot`
4. 列表-评论
5. 列表-私信

所以「列表-评论 / 列表-私信」不是发送节点，只是把已经发生的结果捞回来。发送工作流以后若 C 另做，再登记；v1 不依赖它。

只读核对过的本地 Dify（Community `1.17.0`，地址只写内网主机，不写账号密码）：

- App 名：`douyin-lead-discovery`
- 模式：workflow
- 当前是草稿：已发布版本 0、无 API Key、`tool_published=false`
- 因此现在不能 live 真跑；方案仍按这条契约写

### 6.2 为什么选 Dify，不选 CLI，也不双调

同学 C 那边其实还有 CLI / HTTP。v1 **只认 Dify 这一条契约**：HTTP `POST /v1/workflows/run`。不要既调 Dify 又 subprocess 调 CLI。`difyctl run` 不再采用。

| 方式 | 优点 | 缺点 | v1 结论 |
| --- | --- | --- | --- |
| 调 Dify 工作流 | C 已经把扫描编排写好；我们不碰 cwd/venv；以后她改画布，我们尽量只改映射；发布后走官方 `POST /v1/workflows/run`，不依赖 CLI OAuth | 多一跳：工人 → Dify → C 的 HTTP；草稿未发布时跑不了；必须配 `DIFY_API_KEY`；取消未必能停内层 job | **采用** |
| 调 CLI | 少一跳；命令颗粒度更细（`run/list/send/message`） | 要绑她的工作目录和配置；我们会把她已经编排好的步骤再写一遍；和「Dify 已做好」重复 | **不采用** |
| 同时调两个 | 看起来更稳 | 双发、状态对不齐、取消更乱 | **禁止** |
| 直读她的 SQLite | 字段现成 | 双写会把状态写乱 | **禁止** |

### 6.3 工具对外暴露什么，服务器自己填什么

Dify 输入变量名已经从草稿开始节点读到，实现时按这些名字映射，不要再猜：

```text
base_url, api_token, account, video_id, keyword, limit, channels, no_send, auto_login, list_status
```

Dify 输出：

```text
job_id, run_response, job_status, job_response, snapshot, list_comment, list_message
```

工具给模型的，只留业务字段：

- `account`（必填）
- `keyword` 或 `video_id`
- `limit`
- `channels`
- `list_status`

服务器配置自己填，不让模型碰：

- `base_url` ← `DOUYIN_HTTP_BASE_URL`（C 的 HTTP，只写变量名，不写密码）
- `api_token` ← `DOUYIN_HTTP_API_TOKEN`（只进服务器 `.env`）
- `no_send=false`（v1 锁真发，不要再写死 `no_send=true`，也不是环境变量）
- `auto_login`

`inputs` / `outputs` 仍整份进 `workflow_runs` 的 JSONB，方便以后变量有增减。

一次用户请求通常只调 **一次** `POST /v1/workflows/run`。不要假设还要再调一次发送工作流。短时间相同 `account + keyword + video_id` 要防重入，避免模型连点两次就双发。

## 7. 为什么 v1 改用 Dify 工作流 API Key（`difyctl` 不再采用）

原先想过「可以不配 Dify 工作流密钥」：在服务器上执行一次 `difyctl auth login`（OAuth 设备码，token 前缀 `dfoa_`），配置里只放 App ID。这条路 **不再采用**。

已经撞上的事实：

- 本机 `POST http://192.168.1.158/openapi/v1/oauth/device/code` 返回 404。自建 Dify 默认没开 `OPENAPI_ENABLED` / `ENABLE_OAUTH_BEARER`，设备码登录走不通。
- 用户资源管理器打不开 `difyctl` 安装目录；CLI 登录也先放下，不再当运行时依赖。
- 工作流还是草稿时没有 API Key，所以 live 仍要等同学 C **发布** `douyin-lead-discovery`，再在控制台「访问 API」里创建 Service API Key（`app-...`）。

因此 v1 **会配** 一个工作流 App API Key，但只写服务器 `.env` 的 `DIFY_API_KEY`，不入库、不写本文档、不按 App 用户一人一把。

v1 调用形态：

```http
POST {DIFY_BASE_URL}/workflows/run
Authorization: Bearer {DIFY_API_KEY}
```

```json
{
  "inputs": {
    "account": "<模型填>",
    "keyword": "<模型填>",
    "video_id": "<模型填>",
    "limit": "<模型填>",
    "channels": "<模型填>",
    "list_status": "<模型填>",
    "base_url": "<DOUYIN_HTTP_BASE_URL>",
    "api_token": "<DOUYIN_HTTP_API_TOKEN>",
    "no_send": false,
    "auto_login": true
  },
  "response_mode": "blocking",
  "user": "<我们的 user_id>"
}
```

`DIFY_LEAD_APP_ID` 只给日志和以后切换用，**不是** `/v1/workflows/run` 的必填路径参数。不再采用 `DIFY_COMMENT_APP_ID`、`DIFY_DM_APP_ID`，也不再采用 `DIFYCTL_BIN` / `difyctl run app <app_id>`。

**为什么密钥不按用户存：** v1 整台服务器共用一个 Dify 工作空间。App 里的 `user_id` 只用来隔离我们自己的业务表。按用户映射 Dify 身份是以后的事，token 更不能放到手机上。

HTTP 401 / 密钥无效时，失败分类仍记 `auth_expired`，提示管理员检查 `.env` 里的 `DIFY_API_KEY`。工人不能自己弹出浏览器登录。旧的 `difyctl` 退出码 4 只作为历史对照，不再当运行时路径。

## 8. 部署：给非技术人员用的本地服务器

锁定方案 **B**。

用户不会装 Python、Postgres、Dify。他们下载客户端，连局域网/内网里那台已经部署好的服务器。

服务器上有：FastAPI 工人、Postgres、APScheduler、同学 C 的 Dify、图视频热存储。v1 用 HTTP 调已发布工作流，不再把 `difyctl` 当运行时依赖。

客户端上有：广场、聊天、任务取消、下载媒体、本地缓存。v1 没有「待审列表」产品入口，因为评论/私信不在我们这边审。

**为什么不能做成「每人电脑一份 Postgres」：** 数据会散掉，8 点任务在手关机时跑不了，换手机历史就没了。本地部署 ≠ 数据在手机里。

### 8.1 客户端入口

用户不是技术人员，最后用的是本地部署的服务器 + 下载下来的客户端。入口必须让后端分清「谁」「用哪个智能体」「哪一次对话」：

```text
登录 → app_users / user_id
点击「新建智能体」→ 弹出模板窗（v1 只有 douyin_ops / 抖音运营助手）
填写名称、简介、头像 → 校验名称 → INSERT agent_instances
  同时 INSERT agent_instance_workflows(douyin-lead-discovery)
  同时写入该实例 demo 知识库（agent_knowledge_documents + Store）
广场卡片 → 点击 = 用这个智能体
  → 复用该实例最近一条 status=active 的 app_threads
  → 没有则 INSERT app_threads(user_id, agent_instance_id, thread_id)
之后 ainvoke(..., configurable={thread_id, user_id, agent_instance_id})
```

**为什么要多「智能体实例」这一层：** 「新建智能体」和「开对话」不是同一步。如果只写 `app_threads(user_id, thread_id)`，后端没法记住用户点过「用这个智能体」，广场卡片也无处挂载。v1 一人多实例，表必须按这个模型建。

**名称规则（创建/改名都要执行）：**

- 先 `trim`，空字符串拒绝
- 名称里还有空格、换行、制表符等空白 → 拒绝（空格无效，不算合法名字）
- 在同一 `user_id`、`status <> archived` 的实例中，`lower(title)` 必须唯一
- 大小写不同视为同一个名字，例如 `助手A` 和 `助手a` 冲突
- 已归档实例的名字可以重新使用

**为什么能力只展示：** 用户看懂「这个工人会干什么」即可。勾选会变成按能力裁工具、甚至每实例 compile 新图，和「图不改」冲突，也超出 v1。侧边栏的工作流/工具是目录 × 绑定的只读投影，不是用户勾选框。

**图仍然不改：** `START -> chatbot -> tools_condition -> tools -> chatbot`。广场、侧边栏、绑定表、知识库都不是图上的新节点。

### 8.2 广场卡片

每张卡片对应一行 `agent_instances`，要有：

| 卡片上看到的 | 数据从哪来 | 说明 |
| --- | --- | --- |
| 头像 | `agent_instances.avatar_uri` | 存在实例上，不走 `media_assets` 的 7 天过期文件 |
| 名称 | `title` | 用户填写，受唯一规则约束 |
| 简介 | `intro` | 用户自己写的卡片短介绍，不是应用描述 |
| 模式 | `agent_mode` | v1 固定展示「单智能体模式」 |
| 创建时间 | `created_at` | INSERT 时写入，之后不变 |
| 最近编辑时间 | `updated_at` | 只在改名称/简介/头像时更新。点进对话不算最近编辑 |

不做广场标签、收藏、模型筛选。

### 8.3 对话侧边栏

点进卡片后，中间是对话框，右侧只读，对标元器侧边说明：

| 侧边栏板块 | 数据从哪来 | v1 行为 |
| --- | --- | --- |
| 应用描述 | 模板目录 `capability_description` | 告诉用户这个智能体有什么功能。不是 `SYSTEM_PROMPT`，也不是用户填的 `intro` |
| 应用开发要点 | 模板目录 `development_notes` | 只读说明 |
| 应用设置 / 模式 | `agent_instances.agent_mode` | 只读 `single`。界面可看到「多智能体模式」这个词，但不能切换 |
| 知识库 | `agent_knowledge_documents` | 板块要有。v1 由 demo 种子填充，不开放用户上传 |
| 工作流 | 绑定表 × 目录展示名 | 显示同学 C 的 Dify 工作流名称，例如「抖音线索发现」。不要拿 `workflow_runs` 当侧边栏数据源 |
| 工具 | 绑定表 × 目录 `user_facing_summary` | 给用户看每个工具干什么。不要复用模型 docstring |
| 模型 | 无 | 这一栏先去掉 |

侧边栏全部只读。v1 不让用户在这里开关工具、换模式、改提示词。

## 9. 人工审核为什么表还在，v1 却不审评论私信

这里要分清两件事：

1. **表还按 HITL 设计。** 以后如果产品又要人审，只改开关，不改表。
2. **v1 抖音触达不走审批。** 同学 C 已确认：不用审核；`no_send=false` 时列表-评论和列表-私信对应的是已经真实发布的结果。Dify 在审的话我们这边就不审。

| 通道 | 用在哪 | 机制 | 为什么 |
| --- | --- | --- | --- |
| 对话媒体 | 生图、生视频 | 继续工具内 `interrupt()`，类型 `review_media` | 一次生成挡住当前对话即可，现有审核卡能用 |
| 评论/私信 | C 的 Dify 真发 | 表字段保留 `proposed` / `ready_to_send` / `approved_reply` / `require_approval`，但 v1 `require_approval=false`，**不做待审 API** | Dify 第一步已经发了；我们再审就会「人还没点同意，评论已经出去了」 |

8 点任务以后实现时，也是同一个工具、同样 `no_send=false`。人审开关仍留在 `job_definitions.require_approval`，默认 false。若以后要审批，再把扫描和发送拆开；现在不要假装还能拦下来。

## 10. 同学 C 的链路怎么接到我们的表上

C 的 **链路 B：线索发现 → 评论 / 私信触达**。她原来的产品图仍值得对照，方便排障；但 v1 我们不在自己这边复刻「先扫后审再发」的门禁。

### 10.1 四段（发生在 Dify / C HTTP 内部）

- **B1 登录选视频：** `login / check`，关键词搜索，视频 `discovered → selected`
- **B2 扫描与评估：** 拉评论入库，LLM 打分过滤，生成候选回复
- **B3 评论发送：** `no_send=false` 时在 `POST /v1/commands/run` 里真发，发后核对原文是否出现
- **B4 私信发送：** 同样在这次 run 里真发，发后刷新私信页核对

我们只调用一次 Dify，把输出回写到 `engage_*`。不再打一遍分，不再改她的回复再发给她。

### 10.2 人工门禁（v1 我们不执行）

C 的旧文档里有：run 默认 `--no-send`，账号暂停或状态不是 `ready_to_send` 禁止发送。那是她内部状态机，不是我们 v1 的产品门禁。

v1 明确：

- 不要再把 `--no-send` 当默认
- 不要等 `ready_to_send` 才允许调用 Dify
- 发送失败重试、截图、原文核对由 C / Dify 保证；我们只记最终结果

### 10.3 状态机（表上仍保留，用来落库和排障）

视频：

```text
discovered → selected → scanning → replying | failed | needs_login → completed
```

评论：

```text
proposed → ready_to_send → sending → sent | failed | needs_login | cancelled
```

私信：

```text
proposed → ready_to_send → sending → sent | failed | needs_login | cancelled
```

v1 从 Dify 输出回写时，多数行会直接落到 `sent` / `failed` / `needs_login`。`proposed`、`ready_to_send`、`approved_reply` 列仍在，给以后审批用，不当 v1 必经门。

### 10.4 所有权（避免两套真相）

| 谁 | 存什么 | 角色 |
| --- | --- | --- |
| 同学 C / Dify 自己的库 | 登录会话、全量扫描评论、浏览器动作、重试细节、截图原件 | 运营真相源。「拉评论入库」发生在这里 |
| 本仓库 Postgres | 用户、对话、任务、**被选中的视频**、Dify 返回的评论/私信结果 | 产品真相源 |
| 用户手机/电脑 | 登录态、草稿、已下载图视频、最近会话缓存 | 缓存 |
| LangGraph 官方表 | `checkpoints*`、`store` | `setup()` 生成，禁止 ALTER，禁止拆到手机 |

**为什么不镜像 C 的全量评论：** 扫描量会很大，这才是库膨胀的来源之一。用户要看的是「这次发了什么 / 失败了什么」，不是每一条被丢掉的低分评论。两边用 `platform_video_id` / `platform_comment_id` 对齐。不要直接读 C 的 SQLite。

## 11. 数据库怎么设计

原则：

1. 不改官方 LangGraph 表。官方短记忆靠 `thread_id`，长记忆和知识库向量靠 Store 的 namespace，不靠我们给官方表加 `user_id` 或 `agent_instance_id`。
2. `app_users` 只带用户身份。`agent_instances` 带 `user_id`。对话、任务、触达、媒体、抖音账号投影、工作流绑定、知识库文档元数据同时带 `user_id` 和 `agent_instance_id`。工具从 `RunnableConfig` 读这两个业务 id，不要让模型传「我是谁」「用哪个智能体」。
3. 状态用 `TEXT + CHECK`，词汇跟 C 走，方便对排障。
4. 半结构化、输出样例还可能变的字段用 JSONB。
5. 时间用 `TIMESTAMPTZ`。外键列自己建索引。
6. 给用户看的文案和给模型看的文案分开存：目录配置 vs `prompts.py` vs 用户填写的 `intro`。

对照官方用法：生产 `PostgresSaver` + `PostgresStore`，测试仍 `InMemorySaver`。跨对话记忆的 namespace 从现在的 `("assistant", "profile")` 改成 `(user_id, agent_instance_id, "profile")`。知识库向量走 `(user_id, agent_instance_id, "kb")`。任务幂等不再只写 `("assistant", "jobs")`，改走下面的任务表。

v1 不单独建可编辑的 `agent_templates` 表，也不建 `tools` 表。模板 `douyin_ops`、工作流目录、工具展示文案写在服务器配置里。

### 11.0 这套表覆盖什么、为什么这样拆

| 要回答的问题 | 落在哪 | 为什么不合并 |
| --- | --- | --- |
| 谁登录了 | `app_users` | 身份和智能体不是一回事。没登录就没有后面所有 `user_id` |
| 这个用户有哪些智能体卡片 | `agent_instances` | 广场、侧边栏、名称唯一、最近编辑都挂在实例上 |
| 这个实例绑定了哪些 Dify 工作流 | `agent_instance_workflows` | 绑定会变，目录不会变。密钥不能进这张表 |
| 当前在哪一次对话 | `app_threads` + 官方 checkpoints | 官方表不能加列，所以旁路记归属 |
| 这个实例调用过哪次 Dify、当时状态 | `workflow_runs` | 审计/对账。不要和评论状态机揉成一张宽表 |
| 8 点任务定义和这一次跑到哪 | `job_definitions` / `job_runs` | 定义能取消，运行能取消，两者不是一行 |
| 这次选中的视频/发出的评论/私信 | `engage_*` | 业务状态机，词汇跟 C 走 |
| 这个实例知识库有哪些文件 | `agent_knowledge_documents` | 只存文件元数据。切片和向量在 Store |
| 生图生视频文件在哪 | `media_assets` | 7 天热存储。头像不能放这里 |
| 工具功能说明是什么 | 产品目录，不是表 | 给用户看的摘要会改文案，不必为每个工具建行 |
| 模型短记忆里说了什么 | LangGraph checkpoints | 不要再抄一份聊天业务表 |

关系可以记成：

```text
app_users 1---* agent_instances 1---* app_threads
                         |---* agent_instance_workflows
                         |---* agent_knowledge_documents
                         |---* douyin_accounts
                         |---* job_definitions 1---* job_runs
                         |---* workflow_runs
                         |---* engage_videos / engage_comments / engage_dms
                         |---* media_assets
```

### 11.1 `app_users`

本地多用户。登录这一步只产生 `user_id`，还不等于已经有一个智能体。

| 字段 | 类型要点 | 含义 | 做什么用 |
| --- | --- | --- | --- |
| `user_id` | UUID PK | 用户主键 | 后面所有业务表的隔离键 |
| `login_name` | TEXT UNIQUE NOT NULL | 登录名 | 客户端登录。产品登录以后再做，列先留 |
| `password_hash` | TEXT NOT NULL | 密码哈希 | 只存哈希，不存明文 |
| `status` | TEXT：`active \| disabled` | 账号是否可用 | 停用后不能再开对话、不能跑任务 |
| `created_at` | TIMESTAMPTZ | 注册时间 | 审计 |
| `last_login_at` | TIMESTAMPTZ NULL | 最近登录 | 可选 |

### 11.2 `agent_instances`

一次「新建智能体」一行。这是广场卡片的主表。

| 字段 | 类型要点 | 含义 | 做什么用 |
| --- | --- | --- | --- |
| `agent_instance_id` | UUID PK | 智能体实例 | `ainvoke` configurable 必带 |
| `user_id` | UUID FK NOT NULL | 属于谁 | 广场按用户列出卡片 |
| `template_code` | TEXT NOT NULL | 模板代码 | v1 固定 `douyin_ops`。以后自定义智能体再扩展取值 |
| `title` | TEXT NOT NULL | 用户起的名称 | 卡片标题。创建/改名走第 8.1 节规则 |
| `intro` | TEXT NOT NULL DEFAULT '' | 用户写的简介 | 卡片短介绍。不是应用描述，也不是系统提示词 |
| `avatar_uri` | TEXT NULL | 头像位置 | 持久 URI。不要放进 7 天过期的 `media_assets` |
| `agent_mode` | TEXT NOT NULL DEFAULT 'single' | 模式 | v1 只读 `single`。允许值预留 `multi`，但无切换入口 |
| `status` | TEXT：`draft \| active \| archived` | 实例状态 | 归档后名称可重用，广场默认不展示 |
| `created_at` | TIMESTAMPTZ | 创建时间 | 卡片「创建时间」 |
| `updated_at` | TIMESTAMPTZ | 最近编辑时间 | 只在改 `title` / `intro` / `avatar_uri` 时更新。点进对话不算最近编辑 |

约束：

- 部分唯一：`UNIQUE (user_id, lower(title)) WHERE status <> 'archived'`
- `CHECK (title = btrim(title) AND title <> '' AND title !~ '\s')`
- `CHECK (agent_mode IN ('single', 'multi'))`

不再采用：每个 `user_id` 最多一个 active `douyin_ops`；第二次点新建就复用旧实例。

### 11.3 `agent_instance_workflows`

实例绑定了哪些已发布工作流。自定义阶段先把表建好。

| 字段 | 类型要点 | 含义 | 做什么用 |
| --- | --- | --- | --- |
| `id` | UUID PK | 绑定行 | 内部主键 |
| `user_id` | UUID FK NOT NULL | 冗余用户 | 按用户清数据、授权检查 |
| `agent_instance_id` | UUID FK NOT NULL | 哪个实例 | 入口读绑定、侧边栏列工作流 |
| `workflow_code` | TEXT NOT NULL | 目录里的工作流代码 | v1 只有 `douyin-lead-discovery`。以后可有多条 |
| `enabled` | BOOLEAN NOT NULL DEFAULT true | 是否启用 | v1 新建后为 true；以后自定义可关，但不在 v1 侧边栏暴露开关 |
| `created_at` | TIMESTAMPTZ | 绑定时间 | 审计 |

约束：`UNIQUE (agent_instance_id, workflow_code)`。

明确不进这张表：API Key、Dify App ID、工具 docstring、功能说明副本。展示名和 `user_facing_summary` 永远读目录。

v1 创建 `douyin_ops` 时自动插一行 `douyin-lead-discovery`。

### 11.4 `app_threads`

一次「用这个智能体」对应的对话归属。点卡片时：有最近一条 `status=active` 就复用，没有再 INSERT。

| 字段 | 类型要点 | 含义 | 做什么用 |
| --- | --- | --- | --- |
| `thread_id` | TEXT PK | LangGraph 线程 id | 和官方 checkpoint 对上。官方表不加列 |
| `user_id` | UUID FK NOT NULL | 谁的对话 | 过滤、授权 |
| `agent_instance_id` | UUID FK NOT NULL | 哪个智能体 | 一个实例可以有多条对话 |
| `title` | TEXT NULL | 会话标题 | 客户端会话列表，可后填 |
| `status` | TEXT：`active \| interrupted \| closed \| archived` | 对话状态 | `interrupted` 对应生图生视频 HITL |
| `created_at` | TIMESTAMPTZ | 开对话时间 | 审计 |
| `last_active_at` | TIMESTAMPTZ | 最近一次真正对话 | 可选，用来排「最近对话」。**不是**卡片上的最近编辑时间 |

**为什么要：** 现在线程集合在内存里（`app.state.threads`），进程一重启就丢，也无法按用户、按智能体过滤。点「用这个智能体」时才确保有这一行。

### 11.5 `douyin_accounts`

每个用户在某个智能体实例下的抖音账号 **投影**。不存 cookie。

| 字段 | 类型要点 | 含义 | 做什么用 |
| --- | --- | --- | --- |
| `account_id` | UUID PK | 投影主键 | 内部引用 |
| `user_id` | UUID FK NOT NULL | 谁 | 隔离 |
| `agent_instance_id` | UUID FK NOT NULL | 哪个智能体 | 不同实例可以绑不同号 |
| `account` | TEXT NOT NULL | 传给 Dify 的账号标识 | 对应工作流输入 `account` |
| `display_name` | TEXT NULL | 界面展示 | 客户端显示 |
| `status` | TEXT：`active \| paused \| needs_login` | 账号状态 | paused / needs_login 时禁止调用 Dify |
| `updated_at` | TIMESTAMPTZ | 最近同步 | 客户端提示「请重新登录抖音」 |

**为什么要：** C 规定账号暂停或 `needs_login` 时她内部会失败。cookie 属于 C 的运行时，我们只记结果。

### 11.6 `job_definitions` / `job_runs`

定义：用户设的「以后按点跑」。运行：某一次 8 点实际跑出来的记录。

`job_definitions`：

| 字段 | 类型要点 | 含义 | 做什么用 |
| --- | --- | --- | --- |
| `job_id` | UUID PK | 定义主键 | 取消定义、列任务 |
| `user_id` | UUID FK NOT NULL | 谁 | 对话取消只能动自己的 |
| `agent_instance_id` | UUID FK NOT NULL | 挂在哪个智能体 | 取消范围、授权 |
| `kind` | TEXT | 任务种类 | v1 预留 `douyin_topic_engage`，以及以后的 `morning_brief` / `hydrate` |
| `cron` | TEXT | 调度表达式 | 例如每天 08:00 |
| `timezone` | TEXT DEFAULT `Asia/Shanghai` | 时区 | 不要跟服务器系统时区混 |
| `enabled` | BOOLEAN NOT NULL DEFAULT true | 定义是否还跑 | 取消定义 = false。已 sent 不撤回 |
| `require_approval` | BOOLEAN NOT NULL DEFAULT false | 以后是否人审 | v1 默认 false，不做待审 API |
| `payload` | JSONB | 话题、是否评论、是否私信等 | 半结构化，避免过早拆列 |
| `created_at` / `updated_at` | TIMESTAMPTZ | 审计 | 改开关算编辑定义，不算智能体卡片编辑 |

`job_runs`：

| 字段 | 类型要点 | 含义 | 做什么用 |
| --- | --- | --- | --- |
| `job_run_id` | UUID PK | 这一次运行 | 取消当前 run |
| `job_id` | UUID FK NOT NULL | 属于哪条定义 | `UNIQUE (job_id, scheduled_for)` 防同一点钟跑两遍 |
| `user_id` / `agent_instance_id` | UUID FK | 冗余隔离 | 对话取消按这个范围找 |
| `scheduled_for` | TIMESTAMPTZ | 计划执行点 | 幂等键的一部分 |
| `status` | TEXT | 运行状态 | `scheduled \| running \| waiting_review \| sending \| succeeded \| failed \| skipped \| cancelled` |
| `error` | TEXT NULL | 失败摘要 | 给任务页看 |
| `started_at` / `finished_at` | TIMESTAMPTZ NULL | 实际起止 | 排障 |

`waiting_review` 仍留着，给以后审批用。v1 抖音 8 点实现时，一次 `discover_douyin_leads`（`no_send=false`）跑完就 `succeeded` / `failed`，不进待审。

**为什么现在就建：** 实现可以后做，但「每天八点评论私信某话题」已经确定要有。没有定义表和运行表，后面只能继续滥用全局 Store 键，多用户会串。

### 11.16 运行时怎么串起来

```text
登录 → app_users / user_id
新建智能体 → INSERT agent_instances
  → INSERT agent_instance_workflows(douyin-lead-discovery)
  → seed demo KB → agent_knowledge_documents + Store(user_id, agent_instance_id, "kb")
用这个智能体（点卡片）→ 复用或 INSERT app_threads
之后 ainvoke(..., configurable={thread_id, user_id, agent_instance_id})
  configurable.allowed_workflow_codes ← 绑定表

用户取消 -> 见第 13 节
```

今天代码里的缺口，实现时要改掉：

- 没有 `agent_instances`，也没有「新建智能体 / 用这个智能体」这两步落库
- `PROFILE_NAMESPACE = ("assistant", "profile")` 是全局的，必须改成 `(user_id, agent_instance_id, "profile")`
- `JOBS_NAMESPACE = ("assistant", "jobs")` 是全局的，改走任务表
- 现有知识库是进程内 `InMemoryStore`、namespace `("kb",)`，且内容是小红书 `knowledge/*.md`
- `main.py` 的 `ainvoke` 现在只传 `thread_id`，要实现时传入 `user_id` 和 `agent_instance_id`
- 现有 `POST /v1/threads` 无用户、无实例，正式 App 不够用
- `app.state.threads` 是内存 set
- 媒体目录还没按用户、按实例分开

## 12. 哪些在服务器，哪些在用户设备

服务器 Postgres：上面所有业务表 + LangGraph 官方表。这是唯一真相源。

服务器磁盘：图视频热文件、C 返回的截图 URI 对应文件、智能体头像文件。图视频会过期；头像按实例持久保留。

服务器 `.env`：`DIFY_API_KEY`、`DOUYIN_HTTP_API_TOKEN`。不是 SQL 行。不再把 `difyctl` OAuth 写进系统凭据当 v1 主路径。

Dify 自己的库：工作流定义和内部日志。我们只留 `workflow_run_id`。

客户端可以有本地 SQLite，但只是缓存：

- `local_session`：登录本系统的 token
- `local_agent_cache`：当前智能体标题、简介、头像、能力文案（只读缓存）
- `local_thread_cache`：最近会话标题/摘要
- `local_drafts`：还没提交的改稿
- `local_media_files`：已下载的图视频（这才是体积大的东西）
- `sync_cursor`：上次拉结果的时间

**不能放客户端当主库：** `agent_instances`、`agent_instance_workflows`、`agent_knowledge_documents`、`job_*`、`engage_*`、`workflow_runs`、`douyin_accounts`、checkpoints。智能体实例标题可以缓存，但 `agent_instances` 不能当客户端主库。

**为什么「数据太多」不能靠拆表到手机解决：** 真正大的是生成文件和 C 的全量扫描。文件让用户下载后服务器可删；扫描全量根本不应进我们的库。把任务表放到手机，手关机 8 点任务就停了。

## 13. 定时任务：先建表，后实现，必须能取消

例：「每天八点定时抖音评论和私信某相关的话题」。

调度仍用 FastAPI lifespan 里的 APScheduler。OSS 没有 LangGraph Platform Cron，不要假造。时区 `Asia/Shanghai`。任务在服务器跑，不依赖手机在线。

实现可以后做，但表和取消规则现在锁死。以后 8 点也是同一个工具、`no_send=false`。

### 13.1 一次 8 点怎么走

```text
08:00 APScheduler
  -> 若定义已被取消/关闭：不创建 run，或 run=skipped
  -> job_runs = running
  -> 若抖音账号 paused / needs_login：禁止调用，run=failed 或 skipped
  -> discover_douyin_leads / POST /v1/workflows/run（no_send=false）
  -> 写入 workflow_runs + engage_videos / engage_comments / engage_dms
  -> 聊天或任务页告知扫了什么、发了什么、失败了什么
  -> succeeded | failed
```

对话里「帮我评这个话题」用同一套表，只是 `job_run_id` 为空、`thread_id` 有值。

### 13.2 取消：手动也可以，对话也可以

用户必须能停掉任务，不能「设了 8 点就只能改数据库」。两条入口，写同一张表。

**取消以后都别跑（取消定义）**

- 客户端关掉开关
- 或用户说「以后每天八点这条停掉」「取消那个定时评论」

结果：`job_definitions.enabled=false`。以后到期不再创建 `job_runs`。已经 `sent` 的评论/私信不撤回。

**取消这一次（取消当前 run）**

- 任务页点取消
- 或用户说「今天这条别发了」「取消这次抖音评论」

结果：当前 `job_runs.status=cancelled`。还没发出去的本地行改为 `cancelled`。已经 `sent` 的不撤回。

**正在跑时取消**

- 我们标 `cancelled`
- **未必能停 Dify/C 已在发的任务**（她的轮询和 HTTP job 我们控不住）
- 结果回来后：不再当成功任务展示；能识别未发送的不再二次调用；已 `sent` 不撤回
- 已成功/已失败：不能再取消，只能关掉以后的定义

**对话取消怎么接图**

现有 ToolNode 里加 `list_jobs`、`cancel_job`（名称实现时再定，保持英文）。从 `RunnableConfig` 读 `user_id`，只能取消自己的任务。不要为取消再加图节点，也不要靠模型「口头答应取消」却不写表。

**手动取消**

客户端走 HTTP，例如 `POST /v1/jobs/{job_id}/disable`、`POST /v1/job-runs/{run_id}/cancel`（路径实现阶段可微调）。和对话工具改同一行数据。

取消是一等状态，不要用删行表示。删了就无法解释「8 点为什么没发」。

## 14. 配置与密钥

实现时扩 `.env.example`，不覆盖用户现有 `.env`。文档只写变量名，密钥保持空。C 发布前这几个值都可以空着。

v1 新增：

```text
DIFY_BASE_URL=http://192.168.1.158/v1
DIFY_API_KEY=
DIFY_LEAD_APP_ID=douyin-lead-discovery
DOUYIN_HTTP_BASE_URL=
DOUYIN_HTTP_API_TOKEN=
```

| 变量 | 谁给 | 干什么 |
| --- | --- | --- |
| `DIFY_BASE_URL` | 本机 Dify 地址 + `/v1` | 拼 `POST /v1/workflows/run` |
| `DIFY_API_KEY` | 同学 C 发布后，控制台「访问 API」的 `app-...` | 鉴权调 Dify。只进服务器 `.env` |

| `DOUYIN_HTTP_API_TOKEN` | 同学 C 的 HTTP，对应开始节点 `api_token` | 同上，只进 `.env` |
